# Webhooks

The Webhooks page manages outbound webhooks: HTTP endpoints that receive an event when something changes in the organization. A user creates a webhook, or edits one, on a page of its own by choosing the events it subscribes to and the URL to call, reveals and copies its signing secret, deletes it, and follows its deliveries: a strip of each webhook's recent deliveries in its row, a dialog with the body sent, the endpoint's response and every attempt of each delivery, which it can resend, and the History tab, one row per attempt across every webhook.

## Routes

| URL | Route file | Renders |
| --- | --- | --- |
| `/integrations/webhooks` | `app/src/routes/integrations/webhooks/route.tsx` (layout) and `index.tsx` | `WebhooksPageContent` around the Events tab, which is `WebhookList` |
| `/integrations/webhooks/history` | `app/src/routes/integrations/webhooks/history.tsx` | `WebhookHistorySection`, the History tab |
| `/integrations/webhooks/new` | `app/src/routes/integrations/webhooks_/new/index.tsx` | `WebhookFormPage`, the create page |
| `/integrations/webhooks/$webhookId/edit` | `app/src/routes/integrations/webhooks_/$webhookId/edit.tsx` | `WebhookFormPage` for that webhook, the edit page |

`route.tsx` answers not-found where webhooks are not served to the organization (see Availability below), through `requireWebhooksServed` from `@/domains/webhooks`, sets the "Webhooks" breadcrumb title and renders `WebhooksPageContent` (header and route tabs) around an `Outlet` in a Suspense boundary. It guards the list and the history only. The two form pages sit under `webhooks_/`: the trailing underscore keeps them out of that layout, so the Events and History header and tabs are not drawn above the form, and so they do not inherit its `beforeLoad` either. Each calls `requireWebhooksServed` itself. The create page has nothing to load (`pendingComponent: () => null`). The edit page's `beforeLoad` then reads the webhook with `loadWebhookForEdit` (the list entry, else `GET /webhooks/{webhookId}`; an unknown id is the API's 404, the not-found page), titles the breadcrumb and the tab with `webhookDisplayName` (the host of the URL, never the URL, which is a credential for Slack and Google Chat) and renders the page keyed by the webhook's id. The list loader calls `ensureQueryData(webhooksQueryOptions)`. The history loader loads the history and the list, because the history resolves a webhook's URL from the list. The side navigation entry comes from `integrationsSubRoutes` in `app/src/routes/-components/side-nav/side-nav.constants.ts`.

In this page, a path inside the feature is relative to `app/src/features/webhooks/`. Any other path starts at the repository root.

There is no `store/`: everything the feature holds is server state in TanStack Query, plus local component state and the form's own state in TanStack Form. The local state is the secret's visibility, the picker's search and open groups, the deliveries dialog's webhook and open flag (in the list controller), its selected delivery and, on a phone, which pane shows, the attempt a detail shows, and the History tab's clicked entry. Each dialog keeps its webhook or entry while it closes, so the closing animation keeps its content. The resend watch is a ref (`useDeliveryWatch`): nothing renders from it.

## Data

The webhook endpoints are not described by `app/openapi.yaml`, whose `webhooks` section declares the events, not these paths. There is nothing to generate, so `webhooks.api.ts` calls the shared `client` (`@/api-client/client.gen`) by hand, with the local types of `types/index.ts`. `lib/api/bootstrap.ts` initializes that shared transport before routes, including the base URL, current bearer token and `ApiError` wrapping. See [Generated code](../../../docs/AI_CONTEXT.md#generated-code).

The response shapes below are the types the client declares for each call. Nothing in this repository serves these paths.

| Call | Request | Used by |
| --- | --- | --- |
| `getWebhooks` | `GET /webhooks`, a list of webhooks | `webhooksQueryOptions` |
| `getWebhook` | `GET /webhooks/{webhookId}`, one webhook with its `signingSecret`; an optional `{ cache }` skips every cache for the read before a write | `webhookDetailQueryOptions`, `loadWebhookForEdit`, `saveWebhookOnFresh` |
| `getWebhookHistory` | `GET /webhooks/history`, `{ history: [...] }` | `webhookHistoryQueryOptions` |
| `createWebhook` | `POST /webhooks` with `{ eventTypes, url }`, typed as returning the created webhook | `useWebhookMutations` |
| `updateWebhook` | `PUT /webhooks/{webhookId}` with `{ eventTypes, url }`, answered with the webhook without its secret | `saveWebhookOnFresh` |
| `deleteWebhook` | `DELETE /webhooks/{webhookId}` | `useWebhookMutations` |
| `getWebhookMessages` | `GET /webhooks/{webhookId}/messages?limit=&withAttempts=`, a webhook's most recent messages, newest first, one per message, with `{ webhook, messages, summary, hasMore }` | `webhookMessagesQueryOptions` |
| `getWebhookMessage` | `GET /webhooks/{webhookId}/messages/{messageId}`, one message with its payload and attempts | `webhookMessageQueryOptions` |
| `resendWebhookMessage` | `POST /webhooks/{webhookId}/messages/{messageId}/resend`, answered 202 `{ messageId, webhookId }` | `useResendWebhookMessage` |

A webhook is `{ id, eventTypes, url, signingSecret?, createdAt?, updatedAt? }`. `eventTypes` comes back `null` for an endpoint created outside the console without an event filter, so every helper of the form accepts `null` and reads it as no event. A history entry is `{ date, hookId, hookUrl, eventType, status, responseStatusCode?, responseStatusText?, messageId?, attemptId?, responseDurationMs?, triggerType? }`, with `status` one of `success`, `pending`, `fail` and `sending` and `triggerType` `scheduled` or `manual`. `eventType` is empty when the delivery's message could not be looked up. The last four fields are optional because the console and saas-api deploy on their own schedules: an older saas-api sends none of them. In the messages list, `status` is the message's own: a message that failed and waits for a retry is `pending` with `nextAttempt`, and `attemptCount` and `lastAttempt` are left out without attempts. A message read alone carries `payload` (null, with `payloadAvailable: false`, once the delivery provider no longer keeps it), `chatService` for a Slack or Google Chat endpoint (the payload is then the event, not the chat message the endpoint received) and its attempts, newest first; the console sorts attempts itself and never relies on that order. The screens draw a `WebhookDelivery` (`types/index.ts`): one message to one webhook, from a list entry (`statusSource: 'message'`) or from one history attempt (`'attempt'`), mapped in `utils/webhook-deliveries.ts`.

The query keys are hand-written constants, because no generated key exists: `webhooksQueryOptions` uses `['webhooks']`, the history `['webhooks', 'history']`, one webhook's detail `['webhooks', 'detail', webhookId]` (`staleTime` is infinite), a webhook's messages `['webhooks', 'messages-list', webhookId, limit, withAttempts]` (base `webhookMessagesListBaseQueryKey`; retried once, not refetched on window focus, since the table reads one list per visible row) and one message `['webhooks', 'messages', webhookId, messageId]` (base `webhookMessageBaseQueryKey`; `gcTime` 60 s, as the payload can hold customer data; a 404 or a 403 is not retried, except `GetWebhookMessage.NotDelivered` once for a delivery that came from a list, which can be a race right after publication). `invalidateWebhookQueries` invalidates the list and history keys; because `['webhooks']` is a prefix of every key, it reaches the others as well. `invalidateWebhookDeliveryQueries(queryClient, webhookId, messageId)` runs after a resend: the history (exact), the webhook's message lists (prefix) and the message (exact), never the list of webhooks. `useWebhookMutations` (`createWebhook`, `updateWebhook`, `deleteWebhook`) updates the list cache with `setQueryData` first, then invalidates the webhook queries: create and update upsert the returned webhook into the list (in place for an update, which keeps the order), delete removes the webhook from it. The detail entry, which holds the secret, is invalidated by the prefix, never overwritten. An error shows `toast.error(getApiErrorMessage(error))`, and an update refused with a 404 (the webhook was deleted meanwhile) also invalidates the webhook queries, so the list forgets it. The mutations show no success toast: the form hook does, for create and update.

`updateWebhook` runs `saveWebhookOnFresh` (`queries/webhook-save.ts`): `PUT` replaces both members, so the save re-reads the webhook with `FRESH_READ_OPTIONS` and sends only what the form changed, through `writeOnFresh` (see [forms](../../../docs/03-patterns/forms.md)). The opened values, the edited values and the fresh read are all restated by the same functions of `utils/webhook-form-values.ts` (URL trimmed, events in catalogue order), so that "unchanged" means unchanged. A URL changed in another tab survives a save that changed only the events here; the events are one array, replaced whole when the form changed them. A webhook deleted meanwhile fails the read with a 404, and nothing is written.

The form's schema, `webhookFormSchema` (`schemas/webhook-form.schema.ts`), is a plain `z.object`: at least one event type, and a trimmed URL whose scheme is http or https. It does not start from a generated schema, for the same reason as the calls.

The feature has no GraphQL document.

Scopes: the token picker offers `read:webhooks` and `write:webhooks` (`app/src/lib/api/scopes.gen.ts`). No operation of `api/` enforces them (see `Webhooks` in `api/pkg/scope/scope.go`); saas-api, which serves these paths, asks `read:webhooks` for the reads and `write:webhooks` for the writes and the resend. The screens check one scope themselves: Resend is disabled, with the reason, for a session whose token lacks `write:webhooks` (`WRITE_WEBHOOKS_SCOPE`, `useGrantedScopes`); the other writes are offered and refused by the API. A delivery's payload is customer data readable under `read:webhooks`: it is never logged, kept in no store and dropped from memory a minute after its dialog closes.

## Behaviour

**Availability.** The paths above are not served by the API in `api/`, and the stack in `compose.yml` does not route `/api/webhooks` to a service either (see the header of `docker/envoy/kaiten.yaml.tmpl`, and the [README](../../../../README.md) for what a deployment adds). Kaiten Cloud's saas-api serves them, and only to an organization whose Kaiten licence grants it webhook events: `webhooks` is a NUMBER entitlement, the events it may publish each calendar month, and a grant of 0 (or none) is answered 403 `Webhooks.NotEntitled` on every route, and 503 when the licence cannot be read. Any other grant serves them, and creating endpoints is never limited: the licence counts the events delivered, not the endpoints, so the console shows no quota on the create. The console reads the answer off `GET /webhooks` (asked only where webhooks can exist: Cloud's builds, which name their platform, or a dev or e2e build started with `VITE_KAITEN_WEBHOOKS=true`) through the [`webhooks` domain](../../domains/webhooks/README.md): where webhooks are not served, the side navigation leaves out the Webhooks entry (`needsWebhooks` in `integrationsSubRoutes`), `route.tsx` answers not-found for the list and the history, the two form routes answer it for themselves, and the token scope picker leaves out the `webhooks` scope. Where the answer could not be read, the route renders `RouteError` (`app/src/components/route/route-error.tsx`), an error card with a retry button.

**Events tab.** `WebhookTable` lists each webhook's events (by name, such as `CUSTOMER_CREATED`), URL, masked signing secret and creation date, newest first. The creation date is the only sortable column; the Deliveries column sits between the URL and the secret (below). When the event summary is truncated, a tooltip lists the events by group. A search box filters on the URL and on each event's type, name, label and group title. "New Webhook" is a link to the create page. Each row has two actions (`webhook-table-actions.tsx`): Edit, a link to the edit page, labelled "Edit webhook" with the host and not preloaded on hover (its route may read the API), and Delete, which asks for confirmation and names the webhook's URL. Neither is hidden from a session that may not write webhooks: the API refuses it with a 403, shown in a toast.

**Create and edit page.** `WebhookFormPage` serves both: a create when it has no webhook (`POST`), an edit otherwise (`PUT` through `saveWebhookOnFresh`). It is a full page, not a dialog, because the catalogue holds 123 events. The header stays in place and the body scrolls (`Page layout="scroll"`). From `lg`, the catalogue fills the left and a column on the right holds Destination, Selection and the actions; that column stays in view while the catalogue scrolls (`sticky`), capped to the height of the scroller so the actions never fall below the fold, the chip list taking what is left. Below `lg` the page is one column that reads Destination, the catalogue, Selection, then the actions (`order-*`), while the DOM, and so the tab order, keeps the URL first.

- **Destination** holds the URL. A Slack incoming webhook (`hooks.slack.com/services/`) or a Google Chat one (`chat.googleapis.com/v1/spaces/`) shows a polite notice that it receives chat messages, not the raw event, as saas-api applies a transformation to it (`utils/webhook-chat-destination.ts`, the same tests as saas-api's). A Slack workflow URL gets none.
- **The picker** (`components/webhook-form/event-picker/`) lists the catalogue by group, every group folded at first. Each group header has a checkbox for the whole group, checked, unchecked or mixed, a title that folds its rows, and its count ("3 / 13"). A row is the event's label, with the NAME its payload carries on the right. The search matches each event's label in the viewer's language, its NAME (with or without underscores) and its type, ignoring case and accents, every term of the query required; group titles are not searched. While a search is active, only matching rows and their groups show, open, and the group checkbox acts on the matching rows only (its label says so). Three presets check a set of events, or uncheck it when every one of them is checked: Instance lifecycle (7 events: created, updated, deleted, deployed, migrated, status and lifecycle stage changed), Billing (30: subscriptions, invoices and payments; add-ons, vouchers and checkouts stay explicit choices) and Usage alerts (6: the usage warning, reached, cap and maximum events, an AI model use not authorized, and a usage report rejected). `utils/webhook-event-presets.ts` and its test say what each leaves out and why.
- **Other events** closes the list when the webhook holds types the picker does not offer (an event kept out of the picker, or one newer than the console): they stay selected unless unticked, and a note says so. A webhook without an event filter opens with a notice that it receives every event, and no event selected.
- **Selection** counts the events and shows them by group as removable chips: one "All n events" chip for a whole group, else one chip per event by its NAME. "Clear all" empties it. After a removal the focus goes to the next chip, else the previous one, else the card's title.
- **Saving.** The selection is always kept in catalogue order, so the value can be compared. Create stays disabled until the form is valid; Save also stays disabled until the values differ from what the page opened with. That is TanStack Form's `isDefaultValue`, not `isDirty`, which stays set once a field changed: an event unticked then ticked again leaves Save off. A success shows "Webhook created" or "Webhook updated" and goes back to the list. A refusal shows the API's words in a toast and leaves the form as typed. Cancel goes back to the list without asking. There is no form recovery: the URL may be a credential.

**Deliveries column.** `WebhookDeliveriesCell` reads each visible row's own 20 most recent messages without attempts (`useWebhookDeliveries(id, { limit: 20, withAttempts: false })`), without suspending: a row shows a skeleton (`aria-busy`) while it reads, "Deliveries unavailable" with Retry once its read failed after one retry, "No deliveries yet" when there is none, and otherwise a button holding the strip and one line. The strip is one bar per message, oldest on the left: green delivered, red failed, amber retrying (failed, a retry scheduled), grey pending, grey and pulsing being sent (`DELIVERY_STATUS_PRESENTATION` in `webhook-delivery-status.ts`, shared with the chronology and the badges). The line says when the newest delivery was published, in the viewer's language, and the worst state among the 20: "3 minutes ago · 2 failures", else retrying, in flight, or "all delivered" (`utils/webhook-deliveries-summary.ts`). The strip is hidden from assistive technologies: the button's name says the same ("Deliveries of ops.example.com: 3 minutes ago · 2 failures. Open details."), naming the webhook by its host, never by its URL, and a tooltip gives the counts. A background read that fails keeps the last good strip. The column is not sortable: its data is not in the row model. The table has `getRowId` and the list's handlers are stable, so a row keeps its revealed secret and its focused button when the list is read again.

**Deliveries dialog.** The cell's button opens `WebhookDeliveriesDialog`, a large dialog held in local state by the list controller (a read-only viewer with one action, see [dialog via route](../../../docs/03-patterns/dialog-via-route.md)); a search that hides the row keeps it open, and a webhook deleted meanwhile closes it. It reads the webhook's 50 most recent messages with their attempts. The header gives the URL and the share delivered over them ("19 / 25 delivered · 76%", rounded down and never 100% while one is not delivered; a delivery in flight counts in the total). The chronology, on the left, lists the deliveries newest first by publication time, so a resend never moves one: a dot coloured by its state, the time to the second, the event's label (its type when the console does not know it, "Unknown event" when the delivery provider no longer names it) and the outcome ("200 · 84 ms", "503 · 3 attempts", "No response · 3 attempts", "Retrying after 1 attempt · next attempt …", "Sending · attempt 1"). "Webhook updated" (when more than a minute after the creation, as saas-api touches a chat endpoint right after creating it) and "Webhook created" close it, from the list's webhook dates. The newest delivery is selected first; a click, Enter or Space selects another, while the arrow keys, Home and End move the focus only. The right pane is the shared detail of the selected delivery. Below `md` one pane shows at a time: the chronology, then the delivery chosen, with "Back to deliveries". With no delivery yet the dialog says so above the webhook's dates.

**Delivery detail.** `WebhookDeliveryDetail` is the one detail of a delivery, in the dialog's right pane and alone in the History tab's dialog. It shows the event, the status badge and the message id; the body sent as pretty JSON with a copy button (titled "Event" with a hint for a chat endpoint, with a caption saying it is re-serialized by the delivery provider, so it cannot verify a signature), or why it cannot be shown (expired, not found, a read that failed with Retry, or an older saas-api that names no message); the response to the selected attempt ("Response · attempt i of n": code, duration, time, "Resent manually", body); and every attempt, oldest first, each selectable. Its status comes from the list's message until the message read shows a newer attempt. Resend queues a manual attempt with no confirmation; it is disabled, with the reason, without a message id, without `write:webhooks`, while the delivery is being sent, and once the body is known to be gone. A 409 or 404 refusal is told in the viewer's language. After a resend the deliveries and the message are read again every 3 s for 15 s, so the new attempt shows as sending, then settles.

**Signing secret.** The secret is masked by default. The eye button reveals it. If the list response already carried it, the cell uses that. Otherwise the cell fetches `GET /webhooks/{webhookId}` through `queryClient.fetchQuery(webhookDetailQueryOptions(id))` and keeps the result for the row. Once revealed, a copy button writes it to the clipboard. A failed load or copy shows an error toast.

**History tab.** One row per attempt, sorted newest first on the client. A row shows the date, the webhook URL, the event, the shared status badge, the response (code, duration and the start of its body, "No response" for a failure without one) and a "View details" button on every row. The button opens `WebhookDeliveryDetailDialog` on the clicked attempt alone, so a refetch that drops it from the history cannot close the dialog; the clicked attempt is the one selected. On an older saas-api, whose entries carry no message id, nothing more is read: the detail shows the clicked attempt and says the body is not reported. In this dialog only the message is read again after a resend; the table behind refreshes once, and keeps its search and filters (`resetOnDataChange: false`). The table row and the filters resolve the webhook URL differently: the entry's `hookUrl`, then the webhook list by id, then the id itself. The filters are:

- a free-text search over the URL, id, event, response text, status code, message id and attempt id;
- the event and the webhook, both quick-access chips with their own search box (`searchable`);
- the status and the date, available in the advanced filter only.

**Events.** A subscription names its events by type, such as `com.kaiten.license.v1.created`: the type the API publishes each event under, and the value a subscription filters deliveries on. The delivery history reports the same type.

- `utils/webhook-event-catalogue.ts` maps every audit event name to its type and to a group. It is typed against the generated `Webhooks` union and against `AuditEventName`, so an event that the API adds, renames or retypes fails the type check until it is listed. An entry looks like this:

  ```ts
  // app/src/features/webhooks/utils/webhook-event-catalogue.ts
  CUSTOMER_CREATED: {
    type: 'com.kaiten.customer.v1.created',
    group: 'customer',
  },
  ```

  The billing events (subscriptions, invoices, add-ons, vouchers) are listed in `utils/webhook-billing-events.ts`, which the catalogue spreads into its own map, so that neither file outgrows the size limit. Their entries are checked the same way, and the catalogue fails the type check while an event is in neither file.

- An event's label is the audit trail's (`resolveEventLabel` from `@/domains/audit-trail`). Group titles are the `Pages.Integrations.Webhooks.EventGroups` keys of `en.ts` and `fr.ts`.
- The three events of an anonymous checkout (`CHECKOUT_SESSION_STARTED`, `_COMPLETED` and `_ABANDONED`) are the group `checkout`, titled "Checkouts", listed after the payments. A vendor provisions its customers from `_COMPLETED`: the events carry the e-mail the visitor typed, the only payloads besides the trial reminder that do.
- `group: null` keeps an event out of the picker. Two events have it, `FEATURE_FLAG_EVALUATED` and `ENTITLEMENT_VALUE_GET`. The API triggers them on every flag evaluation and on every read of an entitlement's usage value, so a subscription would receive one request each time.
- A type this build does not know, an event newer than the console, shows as the type itself, under the group "Other events".

**Empty states.** With no webhook, the Events tab shows "No webhooks configured yet." and a hint. With webhooks but no match for the search, it shows "No results". The History tab has its own two states: no delivery yet, and no delivery matching the filters.

## Public API

`app/src/features/webhooks/index.ts` exports `WebhooksPageContent`, `WebhookList`, `WebhookHistorySection`, `WebhookFormPage`, `WebhooksTabs`, `webhooksQueryOptions`, `webhookHistoryQueryOptions`, `loadWebhookForEdit`, `webhookDisplayName` and the `Webhook` type. The three routes under `app/src/routes/integrations/webhooks/` import `WebhooksPageContent`, `WebhookList`, `WebhookHistorySection` and the two query options, and the two under `webhooks_/` import `WebhookFormPage`, `loadWebhookForEdit` and `webhookDisplayName`, as routes are the only importers of a feature (see [Import rules](../../../docs/AI_CONTEXT.md#import-rules)). Nothing imports `WebhooksTabs` or the `Webhook` type from outside the feature.

The feature depends on `@/domains/audit-trail` for `AuditEventName` and `resolveEventLabel`, and on the `filters`, `table`, `page` and `route-tabs` functionals. Whether webhooks are served lives outside it, in `@/domains/webhooks`, because the token scope picker of `service-accounts` needs it too.
