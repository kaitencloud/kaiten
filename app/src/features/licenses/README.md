# Licenses

In the API, one license is one version of a product, and the versions of the same product share a `familyId`. Each version grants entitlements: a limit, a flag or a configuration per entitlement. This feature lists the versions grouped by product (a family), creates a license or a new version of one, opens a version to manage its grants, and moves a version through its lifecycle (publish, archive, unarchive, delete a draft) and its default flag. Where billing is on it also prices a version: its prices, the preview of the invoice they make up, and how the version is sold (its commercial terms), and lists a family in the public catalogue or takes it out.

## Routes

| Path | Route file | What it renders |
| --- | --- | --- |
| `/catalog/licenses` | `app/src/routes/catalog/licenses/index.tsx` | `LicensesPageContent`: the families, each with its versions table |

| `/catalog/licenses/$licenseSlug/prices` | `app/src/routes/catalog/licenses/$licenseSlug/prices.tsx` | `LicensePricesTab`, where billing is on: the prices of the version. `?price=new` and `?price=<id>` open the drawer of a price, `?copyFrom=<version>` offers to finish a copy of prices that stopped |
| `/catalog/licenses/versions` | `app/src/routes/catalog/licenses/versions/index.tsx` | Redirects to `/catalog/licenses` |

| `/catalog/licenses/versions/$licenseSlug` | `app/src/routes/catalog/licenses/versions/$licenseSlug/index.tsx` | `LicenseVersionForm` on the family of that version, which is the base. The breadcrumb reads `New version of <name>`. `?draft=true` offers the version as a draft |

`/catalog/licenses` is an entry of the side navigation (`topLevelRoutes` in `app/src/routes/-components/side-nav/side-nav.constants.ts`). The create and version forms are full pages, not dialogs.

The Prices tab is billing's and the Overview tab is not, so the guard is the tab's own: `routes/catalog/licenses/$licenseSlug/prices.tsx` calls `requireBillingCapability` in its `beforeLoad` and has `BillingNotFound` as its `notFoundComponent`. Where billing is not there the tab is not listed, a link to it explains why in place of the tab, the page of the version stays, and nothing of billing is requested but the capabilities. A version with nothing but its overview shows no bar of tabs, as it had none before it had a second one.

## Data

Reads, REST but for one. The `all*Options` helpers in `app/src/lib/api/all-pages-query-options.ts` keep the key of the generated first-page options and walk every page. The exception is the price of a family, read where billing is on from `useLicensesWithPrices()` of `@/domains/billing`: a GraphQL document of its own that carries every version with its active prices, a page of versions per request, so that no request is made per version. `invalidateLicenseLists` and `invalidateLicenseQueries` refresh it with the lists, since a version published, archived, made the default or renamed changes which version a family is sold by.

- `licensesWithInstancesQueryOptions` (key `['licenses', 'with-instances']`) walks every page of `getLicenses` and `getInstances`, and adds `nbInstances` to each version: the number of instances whose `licenseId` is the version's id. It feeds the list.
- `licenseFamiliesQueryOptions` reads `GET /license-families`.
- `licensesQueryOptions` reads every version; the version forms use it.
- `licenseQueryOptions(licenseSlug)` reads one version.
- `licenseEntitlementsQueryOptions(licenseSlug)` reads the grants of one version.
- `entitlementsQueryOptions` reads the entitlement catalog, which the grant picker offers.
- `licensePricesQueryOptions(licenseSlug)` reads the prices of one version, in the order the API gives them (`display_order`, then id). The Prices route ensures it with the grants and the catalogue, and `useLicensePricing` reads them all.
- `planChangeInstancesQueryOptions(priceId)` finds the instances whose subscription is scheduled to move to a price: every instance, then the subscription of each (`GET /instances/{instanceSlug}/billing`, six at a time, a 404 being no match). The API has no list of the plan changes scheduled and the refusal to deprecate a price they target names no instance, so this is read only once that refusal has happened, and only for a session that may read subscriptions.

The route loaders ensure what their page reads: the list loads the versions with instances and the families; the detail loads the version, its grants and the catalog; the create routes load the catalog, and the version routes also the versions, the families and, for `/catalog/licenses/versions/$licenseSlug`, the base version.

Writes use the generated mutations (`createLicenseMutation`, `publishLicenseMutation`, `updateLicenseMutation`, `associateEntitlementWithLicenseMutation`, `updateLicenseEntitlementMutation`, `deleteLicenseEntitlementMutation`) and the SDK functions `publishLicense`, `archiveLicense`, `unarchiveLicense`, `deleteLicense` and `deleteLicenseEntitlement`. The prices use `createLicensePriceMutation`, `updateLicensePriceMutation` and `deprecateLicensePriceMutation`, which refresh the prices and the version with `invalidateLicensePriceQueries` of `@/domains/billing`; the public listing of a family is `updateLicenseFamilyMutation` (`PATCH /license-families/{familySlug}`, the flag alone), which refreshes the families (`useLicenseFamilyVisibility`); the invoice preview is `previewLicenseInvoiceMutation`, a `POST` that writes nothing; the commercial terms are written by `updateLicenseMutation`. None of them is optimistic: a refusal must never show as a success.

Three helpers in `app/src/features/licenses/queries/license-query-options.ts` invalidate:

- `invalidateLicenseLists` marks the three lists stale: `getLicensesQueryKey()`, the with-instances key and `listLicenseFamiliesQueryKey()`. Only the lists on screen refetch.
- `invalidateLicenseDetails` marks every version's detail stale.
- `invalidateLicenseQueries(queryClient, licenseSlug?)` invalidates the lists and, with a slug, that version's detail and grants, then refetches them all.

A lifecycle transition writes the version the API returns into the detail cache (`setQueryData`) and invalidates the lists. A default change invalidates the lists and every detail, because moving a family's default changes two versions and only the server knows which one lost the flag. A draft deletion invalidates the lists. The create forms call `invalidateLicenseQueries` without a slug, and the grant mutations of the detail page call it with the version's slug.

## Behaviour

- **Families.** Versions are grouped by `familyId`, never by name: a version can be renamed without leaving its family, and two families can share a name. The family is shown under its head version, the `currentVersion` that `GET /license-families` returns; a new version starts from it. A family with nothing published has no `currentVersion` and is shown under its highest version (`getFamilyHeadLicense`). The list, the version picker and the detail never display a license or family slug: a product reads by name and a version by name and number, so two families with the same name look the same.
- **List.** One accordion item per family, sorted by name, with a version count and a `Default: <version>` badge. The first family is open when the page loads. The filters (name, pinned; type; version name; version) run on the client with a 200 ms debounce and survive a refetch, so an action on a version does not clear the search. A filter that hides the head version does not rename the family. "New License" opens `/catalog/licenses/new`; "New Version" opens `/catalog/licenses/versions/$licenseSlug` on the head version and is disabled when the family has none. A row of the versions table opens the version. The controls of the actions cell stop the click from reaching the row. Where billing is on, a family says how its head version is sold in a line beside its badges (see Billing), one that is listed in the public catalogue says so with a Public badge, and its row has a switch to list it or take it out (see Billing).
- **Lifecycle.** A version is a draft, published or archived; a version with no state reads as published. Each state offers one transition: publish a draft, archive a published version, unarchive an archived one. Nothing leads back to a draft. Each transition asks for confirmation, and the dialog keeps the transition it opened for even if the version is refetched meanwhile. The API moves the state only through these operations; an update never sends it. The default version of a family cannot be archived: the button is disabled with the reason, until another version becomes the default or the flag is unset. When the API refuses a transition, the toast shows its message and the version's detail is invalidated, since a refusal usually means the version moved.
- **Default.** "Set as default" is offered on published versions only, disabled with a tooltip on the others. The version that holds the flag shows "Unset default" instead.
- **Delete a draft.** Only a draft offers "Delete" (archiving is for versions that have been on sale). It removes the grants first, then the version, since the API refuses to delete a version that still grants something. Where billing is on, the active prices of the draft that meter a grant are deprecated before any grant goes, since the API refuses to remove an entitlement an active price meters, on a draft as on a published version, and a draft is deleted with its prices anyway: a refusal on a price then leaves its grants and the version in place, and the confirmation says the prices go with it. An instance still on the draft makes the API refuse, and the toast says so. From the detail page a successful delete returns to `/catalog/licenses`.
- **Create a license.** The form has a name (required), an optional slug that follows the name and that the API generates when empty, a type (development, trial, paid or community), a version name, a description and "Save as draft". The version number is assigned by the API. The license is created as a draft, given its grants, then published unless "Save as draft" is checked, so a family never serves a version with half its grants (`useLicenseSave().createLicenseWithGrants`). If a grant or the publish fails, the license stays a draft, a toast says `Saved as a draft, not published: <reason>`, and the app opens its page to finish. If the create itself fails, nothing is saved. Success returns to `/catalog/licenses`.
- **New version.** The body carries the base version's `familyId`, name and type; sending the name alone would open a second product under that name. The family and the base version are selects, locked when the route names the base. The type is the base's and cannot change. Choosing a base fills the description, suggests the next version name (`suggestNextVersionName`: the highest trailing number among the family's names plus one, keeping the zero padding, and nothing for names like "GA") and copies the base's grants into the editor; "Reset" clears them. Opened from a family the form is complete, so it can be submitted without an edit (`allowPristine` while the values pass `licenseVersionFormSchema`). It saves like a new license, as a draft first, and can also start as a draft (`?draft=true` offers it ticked). The body also carries how the base is sold, as far as it is set (`getCommercialFieldsToCopy`): a new version starts with the commercial terms of the version it starts from, as it starts with its description. Where billing is on the form also offers to copy the prices of the base (ticked, `copyPrices`: see below) and says that subscriptions stay on their version until each is scheduled onto the new one.
- **Copy of prices.** Where billing is on, a new version is given the prices of its base too, unless the person declines (the form's "Copy the prices of the base version" is ticked, and what is declined is not even read): the active ones, in display order, one `POST` each (`useCreateLicenseVersion` drives the sequence and `useLicensePriceCopy` the copy), after the grants and before the version is published, since a price meters an entitlement the version must grant and a version must never be served half made. What there is to copy is read before anything is created. The API creates a price at a time and the console cannot make that atomic: a copy that is refused halfway stops, keeps the version a draft with the prices that went through, deletes nothing and sends nothing to the base, and the form opens the new version on its prices with `?copyFrom=<base>`. `PriceCopyBanner` then lists what was copied and what is left (`getPriceCopyState` tells them apart by what each price is, not by how many there are) and "Resume the copy" copies what is left after what is there. What stopped a copy may be fixed on the Overview (a grant the prices meter), so the tabs of the version carry `?copyFrom` and the banner is found again on coming back; it goes when nothing is left to copy. A copy that went through opens the new version on its prices (`getCreatedVersionDestination` says where a new version opens).
- **Grants.** `LicenseEntitlementsCard` lists the grants of a version: entitlement, type, threshold, overage allowance and a remove action. In the create forms it edits a local draft (`useLicenseEntitlementsDraft`) that is sent on submit; on the detail page every add, edit and removal is sent at once. The add dialog offers the catalog entitlements not yet attached. A number grant takes a threshold, or "Unlimited", and an overage allowance; a boolean grant takes on or off; a configuration grant takes a JSON object. A grant an active price meters is kept: the API refuses its removal (`DeleteLicenseEntitlement.MeteredByPrice`) and the toast says why, since the price is deprecated first, on the Prices tab. Any other refusal of a grant shows the reason the API gives; the generic line is for a failure that says nothing.
- **Limits.** A number grant carries the threshold and `limitCapExceededOveragePercent` together, and the API derives enforcement from the pair: `-1` when the threshold is unlimited, `0` for a hard limit, a positive percentage for a soft limit bounded by `threshold × (1 + percent / 100)`. `resolveLimitCapExceededOveragePercent` (`@/domains/entitlement-usage`) mirrors that rule, and every write sends both values, because the API resets an omitted percent to a hard limit. Boolean and configuration grants carry no percent. `NUMBER_AI_CREDIT` is folded into `NUMBER` (`toEditableEntitlementType`), so it gets the same editor.
- **Inline edit.** On the detail page and in the create forms, the threshold and the overage allowance edit in place. A threshold accepts an integer of `-1` or more, or "Unlimited" or an empty value for no limit; an overage allowance accepts a whole percentage of `0` or more, and an empty value means a hard limit. The overage cell is read-only while the threshold is unlimited. Saving one half writes the pair, taking the other half from the row. On the detail page a click on a row opens the entitlement at `/catalog/entitlements/$entitlementSlug`; the inline editors and the remove button stop the click, and a row being saved does not navigate.
- **No edit.** The detail page is read-only apart from the grants, the lifecycle state, the default flag and, where billing is on, the commercial terms. `LicenseForm` has an update branch (its `license` prop) that no route mounts, so the console does not edit the name, type, description or version name of an existing version.

### Billing

Everything below is billing's: it appears only where `GET /billing/capabilities` says billing is on, and each action only to a session whose scopes cover it (`useCanPerform`, `useActionAccess`), both from `@/domains/billing`.

- **The Prices tab.** A table of the prices of the version in the order the API gives them, and a line that says what the version bills: its flat fees, each for its period and joined by "or" since they are alternatives, then each metered price per its own sale unit. Nothing is added up, because a price per unit has no total. A note says what the state of the version means for its prices and, where they can no longer be changed, offers a new version. A price is read as its label (or, with none, what it bills), its shape (flat fee, usage-based, overage), what it meters (an overage states the allowance and the cap it bills against: "Bills above 100,000 traces/month, up to 200,000"), its amount, how it is billed and its status, with the day a deprecated price was retired. A deprecated price stays in the list, in muted text (never an opacity over the row, which would take what it charged and when it was retired under the contrast floor), since subscriptions pinned to it keep being billed from it. Amounts keep every decimal a price has (`formatUnitAmountDecimal`): 0.2 cents reads `$0.002`.
- **What a version lets be done to its prices.** `getPriceRules`: a draft's active prices are edited; a published version's are immutable, and the one change left to a price is deprecation; a new price can be added until a subscription bills the version, which only the API knows, so the console offers it and shows the refusal; an archived version takes no new price. A price that is deprecated is never edited or deprecated again.
- **The price drawer.** A new price and the edit of a price open in a drawer the URL controls (`?price=new`, `?price=<id>`), so that it can be linked to and the back button closes it; a link to a drawer that cannot open (an unknown price, a published version, a session that may not write) leads back to the tab, once the scopes are known (`useActionAccess` tells "not known yet" from "not allowed"). The form picks the shape and how it bills: a metered price is always billed in arrears and has no period of its own, and the form says so. What it may meter is computed from what the version grants (`getMeterOptions`), with no request: a flow (a `NUMBER` or `NUMBER_AI_CREDIT` that resets, summed or counted) is listed; a stock such as seats is listed disabled, with the way to sell it (as an add-on, with a quantity: the hint, `PriceStockHint`, links to `/catalog/addons` where the release ships the add-ons and the session may read them, and names the way and leads nowhere elsewhere); a flag, a configuration and an average are not listed; an entitlement an active price already meters is not offered again; and for an overage the option states the allowance and the cap, and is disabled where the grant is hard or unlimited since it could never bill. The shape and the currency of an existing price cannot change.
- **Amounts.** Typed in the currency's own unit and kept as the string typed (`MoneyField`), converted to the `unitAmountDecimal` the API takes, in minor units, with the string helpers of `lib/money`: 49.00 goes out as `4900` and 0.075 as `7.5`, no float on the way. An amount of more than 12 digits in minor units, or with more than 12 decimals beyond the currency's own, is refused before it is sent, as the API refuses it. A new price takes the currency of the version once it has one, and the display order after its last price; a label emptied in an edit is sent as the empty string, which clears it. The conversion of every body lives in the `*FormValuesToBody` mappers of `schemas/`.
- **Deprecation.** A confirmation says what it changes and what it does not: subscriptions pinned to a flat fee keep being billed from it, it is no longer offered to new subscriptions or to a plan change, a metered price produces no line from the next invoice, and a default price loses its flag in the same write. A refusal is read in the dialog, which stays open. A price that a plan change is scheduled to move to cannot be deprecated until the change is cancelled (409 `DeprecateLicensePrice.PlanChangeTarget`): the dialog shows the API's words as they came and, below them, the instances concerned (`PlanChangeTargetInstances`), each with the date the change takes effect and a link to the Billing tab of the instance, where the change is told and can be cancelled. The refusal names no instance, so they are looked for in the subscriptions once it has happened: while the console looks the dialog says so, and when it cannot read them (the session may not read subscriptions, or a read fails) or finds none, it adds nothing to what the API said.
- **The public catalogue.** A family is private until it is listed, and the catalogue serves the default published version of a listed one. The listing is a billing matter and the API does not gate it on billing, so the console does: the switch of a family (`LicenseFamilyPublicToggle`, a `PATCH` of `isPublic` alone to `/license-families/{familySlug}`) is there only where billing is on, for a session that may write licenses and for a family the API listed (it has a slug to address), and the Public badge only where billing is on. The switch shows what the API answered, not what was clicked: it is off while a change is on its way, a refusal is said in the API's words in a toast and leaves it where it was, and the families are read again once it is accepted. It is named after its family ("List Pro in the public catalogue"), so that a list of switches is not a list of the same name; its caption is not its label, which would name every one of them alike.
- **The invoice preview.** A dialog on the Prices tab (`LicenseInvoicePreviewDialog`, over `InvoicePreviewDialog` of the billing domain) asks the API for the renewal a subscription to the version would be billed: a base price (a select, only when the version has several flat fees, starting on the default; the request names it only when it is not the default) and one sample usage per entitlement an active metered price rates. A quantity is a decimal with a point, checked before sending; empty is no usage. The lines, their arithmetic and the totals are the API's, shown as they came, and the dialog says it is a preview and has no save. The refusal of a sample (`PreviewLicenseInvoice.InvalidSampleUsage`) is shown on the usage, any other under the form. The dialog stays open once the invoice is composed, so the Run button stays focusable while it works instead of dropping the keyboard on the page behind. It works on a draft. A version with no active flat fee cannot start an invoice: the button is disabled and says why.
- **Commercial terms.** The Overview tab shows how the version is sold (pricing type, trial, payment method, call-to-action URL) with an Edit link to `LicenseCommercialDialog`, opened by `?mode=configure` on the layout route like the edit dialog of the other detail pages; the search is dropped on close without touching the other parameters of the tab. The update restates the version, which the API requires, and changes only these fields, which it keeps when an update leaves them out: a trial is cleared with `0` and a URL with the empty string, and nothing is sent for what the version never had (`commercialFormValuesToUpdateBody`). A trial is at least one day and a whole number, a URL is http(s) and at most 2048 characters, each checked on its field; a refusal of the API about a field is shown on that field.
- **How a family is sold.** Where billing is on, the header of a family says how its head version is sold (`LicensePriceSummaryText` of the billing domain, read from `GetLicensesWithPrices`): the flat fee of each billing period, shortest first (the one the version puts forward for the period), "+ usage" when usage is billed on top, "Free" for a free version, "Custom pricing" for one sold on request (whatever prices it has on file), and "No price yet" for one that is sold and has no active price. The amounts are the price's own, in the language of the app: nothing is added up and no monthly equivalent is worked out. The line is left out while the prices are read, when they cannot be read, and for a version whose pricing type the console does not know, and the list never waits for it. It follows the head version, not the highest: the family is shown under the version the API resolves it to.
- **In the list and in the publication.** The versions table has a Pricing column (free, paid, custom) where billing is on, and shows no amount of a version, which the header does for the head version alone. The confirmation to publish says what publishing changes for what the version sells: its prices become immutable, its entitlements freeze once a subscription bills it, and nothing else is touched.
- **A frozen version.** A live subscription freezes the grants and the prices of a version, the prices of a published version are immutable and an archived version takes no new price. The API refuses with a code for each (`getVersionFreezeReason`), and every refusal has the same answer: a new version. `NewVersionDialog` opens for a refused grant (add, edit, remove) or price (a new one, an edit), says what the API said and links to the new-version form started from the version, as a draft. The code tells these from the refusals of another object being billed, and no field says a version is billed, so the refusal is the only signal there is. The drawer closes since there is nothing in it to correct. The way out is offered before any refusal too: the note of the Prices tab, which says why the prices of a published or archived version cannot be changed, carries a "New Version" link (`PriceStateNote`), for a session that may write licenses, to the same form started from the version as a draft (a draft is changed in place, so it has none). It sits in the note rather than among the buttons of the card, which on a phone are already two.

## Public API

`app/src/features/licenses/index.ts` exports `LicensesPageContent`, `LicenseDetailPage`, `LicenseOverviewTab`, `LicensePricesTab`, `LicenseCommercialDialog`, `LicenseForm`, `LicenseVersionForm` and the query options `licensesQueryOptions`, `licensesWithInstancesQueryOptions`, `licenseFamiliesQueryOptions`, `licenseQueryOptions`, `licensePricesQueryOptions`, `licenseEntitlementsQueryOptions` and `entitlementsQueryOptions`. Only the routes under `app/src/routes/catalog/licenses/` import them, as routes are the only importers of a feature (see [Import rules](../../../docs/AI_CONTEXT.md#import-rules)). The invalidation helpers and everything else are internal to the feature.

The table and filter building blocks come from [`functionals/table`](../../functionals/table/README.md) and [`functionals/filters`](../../functionals/filters/README.md).
