# Instances

The detail screen composes `DetailEntityLayout.Top`, Body, Tabs and Content from
`@/functionals/detail-entity-layout`; it owns business labels/URLs and mutations,
while the functional owns fixed/scrollable regions.

An instance is a customer's use of a license: it belongs to one customer, is pinned to one license version for a period, and can be placed on a deployment zone. This feature lists the instances, creates, edits and deletes them, deploys or migrates one to a zone, and shows one instance with its details, its entitlements and usage, its billing where billing is on (its subscription, what it is going through and what may be done to it: moving it to another plan, changing its payment terms, ending it, and the add-ons it holds), and its audit trail. The list is the Instances tab of the customers section, next to [customers](../customers/README.md).

- **Dialogs.** They follow [dialog via route](../../../docs/03-patterns/dialog-via-route.md). `?mode=configure` is validated by the route's search schema, and closing the dialog or saving returns to the detail page without it.

`InstanceDetailProvider` runs `useInstanceDetailViewModel`, which combines `useInstanceDetailData`, `useInstanceDetailDerivedState` and `useInstanceDetailMutations`, and puts the result in context. The tabs read it with `useInstanceDetail()`.

Writes:

- `createInstanceMutation`, `updateInstanceMutation` and `patchInstanceMutation`, called by `InstanceForm`. The lifecycle stage is a PATCH, sent after the create or the update when it is not empty and has changed.
- `updateInstanceMutation` and `patchInstanceMutation` again, from `useInstanceDetailMutations`: renaming the instance in the header (a PUT with the current values) and changing its status (a PATCH).
- `updateInstanceMutation`, from `useInstanceDeploymentMutation`: deploying or migrating.
- `deleteInstanceMutation`, from the table row action and from `useInstanceDetailMutations`.
- `subscribeInstanceMutation`, from `useSubscribeInstance` (`POST /instances/{instanceSlug}/billing`), and `updateCustomerMutation` from `useSetBillingEmail`, which sets the billing e-mail of the customer from the dialog that subscribes. A subscription changes what the tab, the upcoming invoice and the invoices of the instance read, so `invalidateInstanceBillingQueries` refreshes them, and does so too when the API answers that the instance already has a live subscription (someone subscribed it after the tab was read, and the tab behind the dialog must not go on saying it has none); none of these writes is optimistic, since a refusal must never show as a success.
- `cancelSubscriptionMutation` (`POST .../billing/cancel`), `reactivateSubscriptionMutation` (`POST .../billing/reactivate`), `schedulePlanChangeMutation` and `cancelPlanChangeMutation` (`PUT` and `DELETE .../billing/scheduled-change`) and `updateInstanceBillingMutation` (`PATCH .../billing`, the payment terms), from `useSubscriptionLifecycle`, and `detachInstanceAddonMutation` and `updateInstanceMutation`, from `useCancelFollowUps`. Each success refreshes the subscription, its upcoming invoice, its invoices, the add-ons and the instance through `invalidateInstanceBillingQueries`, and so does a 409 that says the subscription is no longer as the tab showed it (`isOutOfDate`: it was canceled, a change was scheduled, a trial ended meanwhile), so that the tab behind the dialog catches up. A 409 that says the period is being closed changed nothing and refreshes nothing. None of them is optimistic.
- `validateVoucherMutation` (`POST /vouchers/validate`) and `redeemVoucherMutation` (`POST /instances/{instanceSlug}/vouchers/redeem`), from `useRedeemVoucher`, and `revokeInstanceVoucherMutation` (`POST .../vouchers/{instanceVoucherId}/revoke`), from the billing domain's `RevokeRedemptionDialog`. A boost applies at once and a discount to the invoices the instance is yet to be issued, so each success refreshes what the instance redeemed, its effective values, its next invoice and the voucher, through `invalidateInstanceVoucherQueries` of `@/domains/billing`. `subscribeInstanceMutation` carries the code of the dialog that subscribes in `voucherCode`; the API redeems it with the subscription, or refuses the subscription. None is optimistic.
- `attachInstanceAddonMutation` (`POST .../addons`), `setInstanceAddonQuantityMutation` (`PATCH .../addons/{addonSlug}`) and `detachInstanceAddonMutation` (`DELETE .../addons/{addonSlug}`), from `useInstanceAddonMutations`. A change applies to the entitlements at once, so each success refreshes the add-ons the instance holds, its effective values (the usage of its entitlements) and the invoice its next boundary will issue, through `invalidateInstanceAddonQueries` of `@/domains/billing`; a refusal that says the list is out of date (the family is already attached, the add-on is no longer there) refreshes it too. `subscribeInstanceMutation` carries the add-ons of the dialog that subscribes in `addOns[]`; the API attaches them with the subscription, all or none. None is optimistic.

Invalidation goes through `@/domains/customer-management` (`invalidateInstancesListQueries`, `invalidateInstanceQueries`, `forgetDeletedInstanceQueries`). They cover the REST instance list, the GraphQL list, the customer queries that derive from instances and, for one instance, its detail. See [query key invalidation](../../../docs/02-conventions/query-key-invalidation.md). Three details:

- After a create, the form stores the created instance under its detail key before the route opens it, so the detail route reads it instead of fetching it.
- After a delete, the detail query is removed, not invalidated: the API hard-deletes the row, and refetching it would fail and retry. The detail page navigates to `/customers/instances` first and reconciles the cache afterwards, because it observes the instance through `useSuspenseQuery`. The table row action does both at once, as nothing observes the row's detail.
- A deployment also invalidates the deployment zone list and the release overview.

## Behaviour

### List

- **Columns.** Name, Customer, CRM Sync, License, Status and Lifecycle (all sortable except CRM Sync), the metadata, and an Actions column. With no active metadata field, the metadata is one raw-JSON dialog column. With active fields, there is one typed column per field and, only when some instance holds keys no active field covers, an "Extra metadata" column. See [metadata fields](../../functionals/metadata-fields/README.md).
- **Filters.** Name (the search box), Description, Customer, License, Status, Lifecycle, and one typed filter per active metadata field. They run on the client. See [`functionals/table`](../../functionals/table/README.md) and [`functionals/filters`](../../functionals/filters/README.md).
- **Actions.** A row opens the detail page. The row actions are Deploy (or Migrate, for an instance that has a zone) and Delete; there is no edit action, which is on the detail page. "New Instance" goes to `/customers/instances/new`, and "Configure metadata fields" to `/settings/metadata` for the `INSTANCE` resource type.
- **Status and lifecycle.** The status is one of Healthy, Degraded, Incident and Maintenance, and reads Healthy when the API sends none. The lifecycle stage is free-form. The console labels Trial, Active, At risk and Churned and shows any other stage as typed. Both come from `@/domains/customer-management`, which the customers screens share.

### Create and edit

`InstanceFormDialog` is a stepped form. The steps are:

1. **Instance information.** Name (at least 3 characters), Slug (creation only), Description, Customer and Lifecycle stage. On creation the slug follows the name and can be edited, and an empty slug is left out so that the API generates one. The customer is locked when the dialog comes from a customer page. The lifecycle stage is a combobox that suggests the four labelled stages and accepts any value; it can be emptied on creation only.
2. **License.** The license version and the license period, which starts today and ends a year later by default. The picker offers every version but the archived ones, plus the instance's own version when it is archived. Options read `<name> v<version>`, with "(draft)" or "(archived)" added. The API refuses to assign an archived version and accepts a draft. The console shows no slug, so two products that share a name read alike.
3. **Deployment.** The deployment zone, optional. It can be emptied while the instance has no zone. Once the instance has one, it can be switched to another zone but not emptied: the API reads an omitted zone as "keep the current one". Switching from this step is a migration, like the Migrate action.
4. **Metadata.** Only when the organization declares active instance metadata fields: one typed input per field. When there is none, the Deployment step is the last and carries the submit button.

On the first two steps, Next stays disabled until the step is valid. Instance metadata is tolerant: the API accepts keys that no active field declares and keeps the values of archived fields itself, but the PUT replaces the metadata as a whole. The metadata step therefore folds the undeclared keys back into the form value on every change, so that saving never drops them. A failed save shows a toast with the API message. After a save, a toast reads "Instance created successfully" or "Instance updated successfully".

### Detail

- **Header.** The instance name, editable in place (at least 3 characters); the status badge, which opens a list of the four statuses and applies the pick at once, with a toast that offers to put the previous status back; and the customer and license names. The actions are Edit (`?mode=configure`) and Delete.
- **Cards.** License Expires (the end date and the time left, in red at 30 days or fewer, in amber at 90 or fewer, and "Expired" once past), Entitlements (the count still under their limit over the total) and Usage Alerts. Usage Alerts carries two figures that count what the table's status badges show: near limit, in amber, for the number entitlements at 80% or more of their maximum allowed usage or into the overage a soft limit tolerates (`NEAR_LIMIT`, `IN_ALLOWANCE`); limit reached, in red, for the ones at that maximum or past it (`AT_LIMIT`, `OVER_LIMIT`). A figure at zero stays neutral. When any near-limit entitlement resets with its current usage window, a helper says how many. Each card's first line starts at the top of the row, even beside a date that wraps on a narrow screen, and its second line (a helper, or the second figure) sits on one baseline at the bottom.
- **Overview tab.** From `xl` the cards sit in three columns: Instance details (name, description, customer, lifecycle stage, created and updated stamps with their author) above the Attio Synchronization card; License (plan, linking to `/licenses/$licenseSlug`, type, version and the period with a progress bar) above Metadata; and Release. The Attio card comes from `@/domains/crm-sync` and renders only when the instance is linked to a CRM record or a sync is in progress. [Detail cards](../../../docs/03-patterns/detail-cards.md) describes the pattern.
- **Metadata card.** One row per active field, rendered by `renderMetadataValue`, the helper the table columns use, so a value reads the same in both. Undeclared keys and values of archived fields sit behind a raw-JSON dialog. With no active field the card shows an empty state.
- **Release card.** The release is resolved from the instance's zone: `instance.deploymentZoneId`, then the zone's current `releaseId`, then that release. The card shows the version and the zone (each a link), the release status as a badge, and when and by whom it was deployed, which is the last update of the zone. The status is the one the releases pages show, from `getReleaseOverviewStatus` over the release of the overview. A release the overview does not hold yet reads from its zone alone: Deployed on a production zone, Staging on a staging or development one. A zone without a release still counts as a deployment: the card reads "Unknown" for the missing parts. An instance without a zone shows an empty state with the Deploy button.
- **Entitlements tab** ("Entitlements & Usage"). The rows are the entitlements granted by the license, matched to the instance's usage; usage that has no grant of the license behind it is an entitlement that only the add-ons the instance holds grant (`source` is `addon`), and is added as a row of its own, named by the catalogue of entitlements and typed by the value the usage carries (`usage-only-entitlement-row.ts`). A group filter narrows the usage card and the table. The tab has no cards of its own: the header's carry the counts. The Usage Overview card draws one meter per number entitlement with its usage window, or "Lifetime" for a counter that never resets, and a soft limit shows its overage allowance. The table has Entitlement (a link to `/entitlements/$entitlementSlug`), Type, Usage (right-aligned, so the meters line up), Threshold, Current window and Status. The threshold is the **effective** limit the usage is measured against (`limit` of the usage of the entitlement): the grant of the license, as the add-ons the instance holds add to it, replace it by or raise it to, which the API composes; the grant of the license alone when a usage carries none. Its overage percent is the effective one as well (an add-on may lower it down to a hard limit). An entitlement counts as enabled until it reaches its maximum allowed usage, which only a number entitlement can.

  **How a limit is composed.** The usage also carries `source` and `provenance`: what the license, the add-ons and the vouchers each contribute. On the threshold of a number entitlement for which the API says how it was composed (`provenance.number` is not null: an add-on or a voucher changes it), the figure is a button that opens a popover, on hover, on a tap, and with Enter or Space from the keyboard (`EntitlementLimitFigure`, in the table and in the usage card): "10,000 license + 3 × 1,000 add-on × 2 voucher = 26,000", each term applying to the total before it (`explainLimit` and `formatLimitExplanation`, `utils/entitlement-provenance.utils.ts`). An add-on replaces the value of the license, raises it (`max(…)`) or adds `quantity × value`; a voucher then sets the value (it replaces the rest), adds to it or multiplies it, and a limit that is unlimited says who grants it. The total is the API's, never worked out here, and a voucher is only ever said by what it does: the API sends no code. There is no popover, and the figure is alone, for an identity row (`number` is null: only the license grants it, and nothing changes it), for a flag or a configuration, and for a provenance the logic cannot read; a layer it cannot read gives none rather than a sum that does not add up. The OpenAPI document declares the `license` and the `number` of a provenance as never null, while the API sends null for them: they are read as possibly absent. When the source is `addon`, "from add-ons" is said beside the limit (`AddonSourceHint`). The popover is closed to the row it is in (`data-row-actions`): opening it does not open the entitlement.
- **Audit trail tab.** It reads the last 200 events of the instance, newest first, and refreshes every 30 seconds. Six cards, in a dense row, count the events: Total Events, Reads, Accepted, Rejected, Warnings and Today. An activity timeline charts them per day, by status (with its own entitlement group and entitlement filters) or by entitlement group. A Value Over Time chart follows the value of a number entitlement, or the total of a group's lifetime counters; it is hidden when the instance has no number entitlement. The event log below has a search box and group, event and status filters, five rows per page, a highlight on rejected events, and a button that opens a dialog with the event, its entitlement and its full JSON payload. A "How Audit Trail Works" card closes the tab. The search box and the three filters act on the event log only; the cards read every event and the charts have their own controls. The status comes from `getEventCategory` in `@/domains/audit-trail`, the function the global [audit trail](../audit-trail/README.md) page uses, so an event has one status on both: read, accepted, rejected or warning. The three usage events that say a limit is approaching, at or past (`INSTANCE_ENTITLEMENT_USAGE_WARNING_THRESHOLD_REACHED`, `INSTANCE_ENTITLEMENT_USAGE_REACHED` and `INSTANCE_ENTITLEMENT_CAP_EXCEEDED`) are warnings: they count on the Warnings card, carry the warning badge, are what the Warning status filter keeps and draw their own series in the activity timeline. `ENTITLEMENT_USAGE_REPORT_ACCEPTED` is accepted, `ENTITLEMENT_USAGE_REPORT_REJECTED` is rejected, and an event the domain does not name reads from its last word (see the audit trail README). Event labels come from `resolveEventLabel` in the same domain.

### Billing

The Billing tab sits between Entitlements & Usage and Audit Trail, and exists only where billing is on and the session may read it: it is absent from the tab bar otherwise, not an empty tab, and its address explains itself. Its cards are fields of the API and the console adds nothing up.

- **Subscription.** Its status, the provider, how it is collected and the payment terms, each said to be the organization's default or this contract's, the base price with its period and timing, the current period in UTC and the next boundary (the instant the period closes and its invoice is composed). A trial says when it ends and when its first invoice is issued in place of the next boundary, a subscription set to cancel says when it ends (`Ends on`), and a subscription that ended keeps its card, with when and why, and offers to subscribe again. An instance that was never subscribed is "Not subscribed", a state and not an error, with a Subscribe link for a session that may write billing (a read-only session sees the state and no button). A version of the license that is not published cannot be subscribed to: the button stays in the tab order, disabled, and the text that describes it says why.
- **Upcoming invoice.** What the next boundary will issue, composed from the usage so far, with the lines on request in a preview dialog. When the API says the invoice would be held (`wouldHold`), a banner names each meter and the check that failed and leads to its usage history (`?history=`).
- **Invoices.** Those of the instance across the times it was subscribed, newest first, in the shared `InvoicesCard` (the customer column is left out, since the page already says whose they are). The card holds them all: its table sorts them and pages them ten to a page in the browser.
- **What the subscription is going through.** Above the cards, one notice per state, each a sentence of its own that says what is still true (`SubscriptionNotices`, from `getSubscriptionNotices`: a subscription that just runs has none, and neither has one that ended). A **trial** says when it ends, how many days are left, that nothing is billed during it and when the first invoice is issued. A subscription **past due** says since when and for how many days, names the oldest invoice that is unpaid past its due date with a link to it, and says that access is unchanged: Kaiten restricts no customer for an unpaid invoice in this version, so there is no countdown. A **cancellation scheduled** for the end of the period says when the subscription ends and why, that the period is paid for, and offers Reactivate, one click away for as long as the notice stands. A **plan change** waiting for the boundary says to which plan, for how much and when, that nothing is prorated, and offers Cancel the change; the API gives the price alone, so the license version it belongs to is found among the versions on sale, for a session that may read them (`licensePrices.read`): while they are read, and for a session that may not, the notice names the price and is no less true.
- **What may be done to it.** Under the card, `SubscriptionActions`: Change plan, Payment terms (Provider and terms where Stripe is offered) and Cancel subscription, each a link to its dialog, there only where the release ships the lifecycle (`features.lifecycle` of the capabilities) and for a session that holds the scope of the action (`useCanPerform`). What the state forbids is not removed but greyed out with its reason, on a button that stays in the tab order: the plan cannot change during a trial ("Unavailable during a trial") or while a cancellation is scheduled ("Reactivate the subscription first"). A subscription that ended has none of them: it is subscribed again. Reactivate and Cancel the change are one click with nothing to fill in (`useLifecycleAction`): one request however often it is pressed, a period being closed is waited out, a refusal that says the subscription is no longer as the screen showed it is told in a toast (the notice the button stood in goes with the refresh; when it is a subscription that ended, the toast has a Subscribe again button that opens the dialog that subscribes it), and any other refusal is shown beside the button, with a Retry for a failure that changed nothing.
- **Cancel dialog.** A route of its own over the tab. It asks when the subscription ends: **at the end of the period**, which is paid for and is the default, or **immediately**; a trial has no choice, it ends at once and bills nothing, and says so. It says what the choice does before it is confirmed (`CancelExplanation`): at the end of the period a final invoice bills what was used in arrears, which may be nothing, and the subscription can be reactivated until then; immediately, the final invoice is issued now, nothing is prorated, what was paid for the period is not refunded and it cannot be undone, in a warning and on a destructive button. Either way it says that a plan change waiting for the boundary is dropped by the cancellation, as the API does. The reason is optional, at most 500 characters counted as the API counts them (code points, not UTF-16 units), with a counter that stays under the field over the limit, beside the refusal that takes the place of the description. Beside the cancellation, two options, both unchecked: remove the add-ons, and set the end date of the license. Cancelling changes billing only, so each is a request of its own, sent once the cancellation is accepted and one after the other (the add-ons first, then the instance, which a PUT replaces as a whole with the one date changed, the end of the period proposed until the person types another, or now for an immediate cancellation); an option the session may not carry out is not offered, and one with nothing to do says so. A failure of one does not stop the rest and undoes nothing: the dialog says what was done and what was not, and tries again only what failed. Once accepted it says what it did: when it ends, or the final invoice with a link to it (when the API issued none, it says so). A refusal leaves the dialog open with what was typed, above the buttons or on the reason when it is about it. The form keeps the subscription as it was when the dialog opened (`useOpenedSubscription`), since cancelling refreshes the tab behind it and the form must not turn into "already canceled" before it has said what it did.
- **Plan change dialog.** A route of its own over the tab. It says the plan the subscription is on, that the change takes effect when the current period ends and never before, and that nothing is prorated. The API cannot compose the invoice of a change that is not scheduled yet, so the console draws none: it shows the upcoming invoice as things stand, the API's own, and says so, and once a change is scheduled it says that the invoice already applies it. The plans are the active flat fees of the license versions on sale, the plan the subscription is on left out, grouped by license name with the newest version first (`buildPlanTargets`); a plan in another currency is listed and cannot be chosen, and says why, since the invoice of the boundary bills the old plan and the new one together in one currency. A change already scheduled is said first, with the way to drop it: choosing another plan replaces it. A refusal about the plan itself (another currency, a price taken off sale since, the same price) is shown on the field, any other (a trial, a cancellation) above the buttons. A subscription that cannot change plan (a trial, a cancellation scheduled, one that ended, an instance never subscribed) says why in place of a form.
- **Payment terms dialog.** A route of its own over the tab: the days between the issue of an invoice and its due date for this contract, said first with where they come from. Where Stripe is offered (connected, or free to be connected) it is the **Provider and terms** dialog (the link and the title say so) and it also changes who collects (Manual hand-off or Stripe; Stripe is listed off, with the way to connect it, while it is not connected) and how (send the invoice, or charge the card on file, which only Stripe can do: the option is listed with "needs Stripe" for the other provider). The request (`PATCH .../billing`) carries each of the days, the provider and the collection method only when it differs from what the contract has, so a change of provider alone sends `{ providerKind }`; a move to the organization's own system sends the invoice, which is all it does, and the form sets the method itself. What the API would refuse and the screen can tell is said before the button: a customer without a billing e-mail, whom Stripe sends the invoices to (the button is off then, as the API would refuse), and one without a payment method Stripe can charge (read with `customerBillingQueryOptions`), each with a link to the customer. When the provider changes, the dialog lists the invoices still open (`instanceInvoicesQueryOptions`) and what becomes of each, from their status, provider and hold (`getOpenInvoiceFate` and `getOpenInvoiceMove` of `utils/provider-switch.ts`): every invoice keeps its own provider, collection method and terms, and the change applies from the next one. A ready-to-bill invoice is settled by marking it paid or writing it off; a held draft is a deliberate choice between releasing it and recomposing it; a draft the queue has, or a push that failed, keeps being pushed to Stripe; a draft Stripe holds for a person waits there (told from a draft the queue has by reading the invoice in full, since the list has no record of the provider); and an invoice Stripe has accepted stays collected by Stripe, so Stripe cannot be disconnected while it is open. Each says how to move it to the new provider (void it, then recompose it). An empty days field is the organization's terms, sent as `null` and not as zero (zero is due on receipt), and so is the Use organization default button when the contract has terms of its own. The change takes effect on the next invoice: the invoices already issued keep their own due date, and the dialog says so. A refusal is shown on the field it is about (the days, the provider, the method) and above the buttons otherwise.
- **A period being closed.** Every write above is refused with a 409 `*.BoundaryPending` while the period that ended is being closed, and nothing was changed. The dialog or the notice says "Closing the period" (`BoundaryClosingNotice`, a status and not an error), sends the very same request again once, after what `Retry-After` says (a minute when it says nothing), and shows the refusal with a Retry only if that second try fails (`useBoundaryRetry` of `@/domains/billing`).
- **Subscribe dialog.** A route of its own over the tab (see [dialog via route](../../../docs/03-patterns/dialog-via-route.md)), a `StackedFormDialog` with the base price (an active flat fee of the version, the default first; a metered or retired price is not offered), the payment terms (empty to take the organization's) and the start of billing in UTC. The start may be as far back as one billing period and never in the future: the form says so before it asks, the API has the last word. The provider is NoOp and is told, not asked. A summary says when the first invoice is issued (`getFirstInvoiceTiming`), and a customer with no billing e-mail is asked for one in the same dialog, without leaving it (a form of its own: Enter there sets the address and does not subscribe, and a refusal of the API takes the focus the disabled field dropped). A refusal of the API is shown on its field when it is about one, above the buttons otherwise, with what was typed kept, and a field refusal goes when the field changes. Where the release has trials (`features.trials`) the dialog asks for one in days, prefilled with the trial the license carries, and says that the first invoice is issued when it ends; a price billed in arrears has none and says so, and the field is not there where the release has no trial. The days are always sent where the release has trials, even when they are none, so that the trial a license carries does not apply behind the back of the person who read the form. The console bounds a trial at 365 days, a bound of its own: the API has none and refuses a longer one as an error of the server. Where the release ships add-ons and the session may read them, the dialog also offers the add-ons the instance can start with (`SubscribeAddonsField`): the versions on sale that fit the license family of the instance, each a box with its units from one to what the version allows (`useSubscribeAddons`). The API attaches them with the subscription, all or none, and checks them as a whole: a refusal of one (`SubscribeInstance.AddonInvalid`, 422) is shown on that field with the reason the API gives for that add-on (its `detail` is the same sentence for every reason, so the field takes the message of the error that locates the add-on) and the subscription does not start. Nothing is offered where the release has no add-ons, and the request carries no `addOns` when none is included. When what the offer is drawn from could not be read, the dialog says so with a way to ask again (`AddonsReadNotice`) and never keeps the subscription from starting; when only some versions could not be checked, the others are still offered and the notice says some are missing. Once started, the dialog says so with the way to the invoice of the first period (or, for a trial, until when it runs), and takes the focus the button that sent the form had.
- **Add-ons.** The Billing tab lists the add-ons the instance holds in a card of their own (`InstanceAddonsCard`), under the subscription and the upcoming invoice, where the release ships add-ons and the session may read them (`instance.addons.list`): the version (the name its attachment carries, and its slug, which says which version it is, since an instance holds one version of a family at a time), the **quantity**, what a unit costs (its flat fee for the period of the subscription, `PriceAmount`; "Free", "On request" or "Not billed" otherwise) and since when. A version withdrawn from sale since is marked and stays listed: the instance keeps it until it is taken off. A note says what any change does: the entitlement changes now, it is billed from the next renewal, with no proration or refund. The quantity is a stepper (`QuantityStepper`) that moves **one unit a click, one request a click**, within one and what the version allows (`getQuantityBounds`), for a session that may set it: it shows what the API holds, never what was clicked, and goes back to it on a refusal, which is told above the list with a way to ask again. **Taking one off** asks first (`RemoveAddonDialog`): its entitlements end at once, the period under way is not refunded and it is no longer billed from the next invoice; an add-on billed in arrears is the exception the confirmation says, its fee for the period that ends at the next invoice being charged in full at the last quantity held. **Adding one** is a route of its own over the tab, offered **only while the subscription lives** (`isSubscriptionLive`: trial, active or past due; an instance nobody bills takes its add-ons with its subscription, in the dialog that starts it, where the API checks them as a whole): the selector (`useAttachableAddons`) lists the versions on sale that fit the license family of the instance, of a family it holds no version of, and says, above the fields, that some could not be checked when a read of one failed (the dialog is a failure of the whole only when nothing is left to offer), the quantity is checked against the version before anything is sent, and the price of the unit for the period of the subscription is said first, with a version that has no default price for that period flagged, since the API will refuse it. A refusal about a field is shown on it, a period being closed is waited out like every change to a subscription (`useBoundaryRetry`), and a double click sends one request. Every change, once accepted, says in a toast **what it did to the effective values** (`useAddonChangeReport`): the usage of the instance is read before and after, and the entitlements whose limit moved are named with both values ("Seats: 20 → 25"), because how an add-on adds to, replaces or raises what the license grants is the API's to compute. A subscription that ended keeps what the instance holds, which can still be stepped or removed but not added to.
- **Vouchers.** The Billing tab lists what the instance redeemed in a card of its own (`InstanceVouchersCard`, the billing domain's `RedemptionsCard` led by the voucher), below its add-ons, where the release ships vouchers and the session may read those of an instance (`instance.vouchers.list`): the voucher, when it was redeemed, the window it applies in, the invoices a discount used of the invoices it can discount and its state, with the reason of a revocation. A voucher leads to its page for a session that may read vouchers. **Applying a code** is a route of its own over the tab (`RedeemVoucherDialog`), for a session that may redeem (`instance.vouchers.redeem`, `write:voucher_redemptions`), in two steps: the code is checked first, and what the API said is shown as the offer in plain language, or as the first check that failed and, for an instance that does not meet the voucher, the condition it breaks; only a code the API called valid can be redeemed, and typing again forgets the verdict, which was about the old code. Once redeemed, the dialog shows what it did, read from the API: for a boost the entitlements whose effective value moved, with both values and until when; for a discount the invoice the next boundary will issue before and after, and how many invoices it will discount. What it did takes the focus the button that redeemed the code had, which is gone with the form. A redemption that still applies can be taken back from its row, with the reason the API requires, by a session that may write vouchers (`write:vouchers`, which is not the scope that redeems). A period being closed is waited out like every change to a subscription (`useBoundaryRetry`). **The subscribe dialog** takes an optional code, redeemed with the subscription, where the release has vouchers and the session may redeem; a code that cannot be redeemed refuses the subscription as a whole and the reason is shown on the field, in the API's words (`SubscribeInstance.VoucherInvalid`, located at `body.voucherCode`).
- **Frozen fields.** While a subscription lives, the customer and the license of the instance cannot change (409 `UpdateInstance.BillingActive`). The API says only that one of them may not, so the form works out which fields were changed from what it opened with, puts the refusal on them in the API's words with a link to the subscription, and takes the person to the step of the first. The refusal goes when the field is put back.

### Usage history

The History link on the row of each number entitlement opens a drawer over the Entitlements tab (`?history=<entitlementSlug>`, so that it can be linked to and the back button closes it). It lists every report accepted for the counter in the order it was accepted, a hundred at a time ("Load more" asks for the reports after the last one read), for a period of days read in UTC (none: the last 30 days, as far back as the organization keeps; the period is the API's filter and lives in the URL with the drawer, `?from=` and `?to=`, so that a link carries it and a reload keeps it, and closing the drawer takes it away), with the report where the limit moved marked and what the instance sent with a report on request. It exports the period as a CSV of up to 366 days (the console names the file, and a longer period keeps the button, disabled, with the reason). A period that reaches before what the organization keeps is not a failure: the drawer says how long usage is kept, where it begins, and offers to start there. The history is the instances', not billing's, and opens with billing off.

### Deploy and migrate

One control covers the two transitions. An instance without a zone is *deployed*, one that has a zone is *migrated*, and both open the same picker. The control is an icon in the list row, and a button on the Release card of the detail page: a header action once the instance has a zone, the main button of the empty state before.

- **Dialog.** It opens with the instance and the zones fetched, shows the current zone when migrating, and lists the other zones as `<name> — <type>`. It says so when there is no other zone, and confirms only once a zone is chosen.
- **No dedicated endpoint.** Deploying and migrating are a `PUT /instances/{slug}` with a new `deploymentZoneId`. The PUT replaces the whole resource, so the dialog fetches the instance and re-sends every writable field:

```ts
// app/src/features/instances/utils/instance-deployment.utils.ts
export const instanceToDeploymentUpdateInput = (
  instance: Instance,
  deploymentZoneId: string,
): InstanceWritable => ({
  customerId: instance.customerId,
  deploymentZoneId,
  description: instance.description,
  endLicenseDate: instance.endLicenseDate,
  licenseId: instance.licenseId,
  metadata: instance.metadata ?? {},
  name: instance.name,
  startLicenseDate: instance.startLicenseDate,
});
```

- **Events.** The API infers the transition from the previous zone and emits `INSTANCE_DEPLOYED` or `INSTANCE_MIGRATED` (`api/internal/modules/instances/updateinstance/handler.go`).
- **After a deployment.** The dialog closes, a toast reads "Instance deployed successfully" or "Instance migrated successfully", and the console tracks `instance_deployed` or `instance_migrated` (`logger.track`) with the instance slug and the previous and the new zone.

### Delete

The row action and the detail header both ask for confirmation, and the text warns that usage history, reported metrics and integration links go with the instance: the API deletes the row for good. A successful delete shows the toast "Instance deleted successfully" and a failed one "Failed to delete item". After a delete from the detail page the console returns to `/customers/instances`.

An instance that bills is kept: the API refuses (409 `DeleteInstance.BillingActive`) while its subscription lives or an invoice of it is not settled, and says which. The console explains it in a dialog and not a toast (`useDeletionRefusal`, `DeletionRefusalDialog` from `@/domains/billing`): the status of the subscription with a link to it, and the invoices to settle, each leading to its page. Nothing was deleted.
