# Folder structure

This page describes each folder of the console. The rules that govern them (layers, import rules, principles) are in [AI_CONTEXT.md](../AI_CONTEXT.md); this page shows where things are and what belongs in each folder. Folder contents change often, so it links to the folders instead of listing them.

## Where `app/` sits

```txt
kaiten/
├── api/            # the Go API
├── app/            # the console, described here
├── charts/         # Helm charts
└── packages/
    ├── api-codegen/    # generates the REST client and the scopes list
    └── theme/          # design tokens (@kaitencloud/theme)
```

```txt
app/
├── .storybook/         # Storybook configuration
├── cel-engine/         # Rust CEL engine, compiled to WebAssembly
├── docs/               # this documentation
├── e2e/                # Playwright suites: tests/ (Storybook), app/ (application)
├── public/             # static assets; public/wasm/ is written by build:wasm, not tracked
├── scripts/            # architecture, file-size, i18n and E2E-contract checks
├── src/
├── codegen.ts          # graphql-codegen configuration
├── openapi.yaml        # the Core API contract (generated from the Go source)
├── platform-openapi.yaml
└── package.json
```

```txt
app/src/
├── api-client/      # generated REST and GraphQL client (git-ignored)
├── components/      # generic UI
├── domains/         # business modules shared by several features
├── e2e/             # Mock Service Worker handlers and seeds, loaded only on request
├── features/        # one folder per product area
├── functionals/     # generic widgets and layouts
├── hooks/           # shared hooks
├── lib/             # infrastructure
├── routes/          # TanStack Router file routes
├── test-fixtures/   # Storybook fixtures and test helpers
├── __tests__/       # unit-test setup
├── env.ts           # runtime environment (the VITE_* values)
├── main.tsx         # entry point
├── routeTree.gen.ts # generated by the router plugin
└── styles.css, tokens.css   # Tailwind entry point, the app's own design tokens
```

`src/e2e/` is test infrastructure, not a layer: `main.tsx` loads it dynamically, only when a `VITE_E2E_MSW`, `VITE_MOCK_API` or `VITE_MOCK_NOTIFICATIONS` variable asks for it, and the production build leaves it out. Its handlers build their seeds from the Playwright models in `app/e2e/app/_support/model/`, and the dev world (`src/e2e/msw/dev-world/`) its records with the fixture builders of `app/e2e/app/_support/fixtures/`. The unit-test server (`src/__tests__/msw-server.ts`), the Storybook configuration (`.storybook/msw.ts`), `src/test-fixtures/` and a few unit tests read the billing capability profiles of `app/e2e/app/_support/model/billing-capabilities.ts` the same way. These dependencies are ones that `check:architecture` cannot judge, because their target lies outside `src/` and no rule covers it.

## Dependency matrix

A row is the folder that imports; a column is the folder it imports from. `pnpm run check:architecture` refuses every "no" (see [Import rules](../AI_CONTEXT.md#import-rules) for the rule names and the two warnings).

| From \ To | `lib/` | `hooks/` | `components/` | `functionals/` | `domains/` | `features/` | `routes/` | `api-client/` |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `lib/` | yes | no | no | no | no | no | no | yes |
| `hooks/` | yes | yes | yes | no | no | no | no | no |
| `components/` | yes | yes | yes | no | no | no | no | no |
| `functionals/` | yes | yes | yes | yes | no | no | no | no |
| `domains/` | yes | yes | yes | yes | yes | no | no | yes |
| `features/` | yes | yes | yes | yes | yes | own feature only | no | yes |
| `routes/` | yes | yes | yes | yes | yes | yes | yes | yes |

The check enforces six core invariants:

- no import between two features, not even for a type;
- `features/<name>/index.ts` is reserved for routes;
- `components/` imports none of `api-client/`, `domains/`, `features/`, `functionals/` or `routes/`;
- no import of `features/`, `domains/`, `routes/` or `api-client/` from `functionals/`;
- no import of `features/` or `routes/` from `domains/`;
- a functional is always imported from outside through `@/functionals/<name>`.

It also enforces the `hooks/` and `lib/` rows, that a feature never imports `routes/`, and that the `rollout`, `targeting` and `variants` submodules of `features/feature-flags` stay private to that feature. Files outside these folders (`env.ts`, `main.tsx`, `e2e/`, `test-fixtures/`) are not layers: the matrix has no row for them, but the public-API rules apply to them as importers. They cannot import a feature's `index.ts`, since only routes may, nor a private `feature-flags` submodule, and they import a functional only through `@/functionals/<name>`.

A "yes" still goes through a public entry point: `@/features/<name>` from routes only, `@/functionals/<name>` for a functional, `@/domains/<name>` for a domain (see [Import rules](../AI_CONTEXT.md#import-rules)). A route can load a domain's query options. That does not hand the screen to the domain: the screen stays in the route-facing feature.

## `api-client/`: the generated client

Generated by `pnpm run generate` from `app/openapi.yaml` and the GraphQL schemas, and git-ignored: it does not exist after a clone until the command runs. Never edit it. [api-generation.md](./api-generation.md) explains what is generated and how to use it.

The client has several entry points; the `@/api-client` barrel exports only the SDK functions and the types.

| Import | What it gives |
| --- | --- |
| `@/api-client` | The SDK functions (`listCustomers`) and the types (`Customer`) |
| `@/api-client/@tanstack/react-query.gen` | The query options (`getFeatureFlagOptions()`), the mutations (`createFeatureFlagMutation()`) and the query keys (`listCustomersQueryKey()`) |
| `@/api-client/zod.gen` | The Zod schemas (`zCustomer`) |
| `@/api-client/msw.gen` | One Mock Service Worker handler per operation (`handleListCustomers()`), for the mocks, the tests and the stories only |
| `@/api-client/graphql`, `@/api-client/graphql/graphql` | The `graphql()` document function; the types generated for each document |

The REST client is configured by `src/lib/api/bootstrap.ts`, imported before the route tree. It calls `configureApiClient` once before query keys capture the base URL; importing adapters has no initialization side effect. See the [API infrastructure README](../../src/lib/api/README.md).

## `components/`: generic UI

[`src/components/`](../../src/components/) holds UI with no business logic and no business name (no `customers-*`, `licenses-*`, `feature-flags-*`).

| Folder | What it holds |
| --- | --- |
| `ui/` | The primitives (`Button`, `Input`, `Badge`, `Card`, `Popover`, `Separator`, `Table`) and shadcn/ui's Base UI components (`Dialog`, `Select`, `Tabs`, `Tooltip`, `NumberInput`, ...). The only folder allowed to import `@base-ui/*`. |
| `form/` | The form system: field components in `fields/`, `FormItem`, `FormLabel`, `FormMessage`, `SubmitButton`. The `useAppForm` hook that assembles them is in `src/hooks/form.ts`. |
| `dialog/` | Shared dialogs: the form dialog and the delete confirmation. |
| `route/` | `RouteError`, `RoutePending`, `NotFound`, `RestrictedAccess`. |
| top level | Generic components such as the date picker, the combobox and the theme provider. |

Import `ui/` components directly (`@/components/ui/button`) from any layer above `lib/`: `lib/` may not import `components/`. `cn` is in `@/lib/utils`.

Placement:

- A component tied to one business domain belongs in `features/<name>/components/`.
- A generic component that grows complex and serves several independent consumers moves to `functionals/`.
- Shared business logic goes to `domains/`, not to `components/`.

## `features/`: product areas

[`src/features/`](../../src/features/) is the core of the app. Each feature is a self-contained module with a route-level public API.

- `features/<name>/index.ts` exports what the routes consume, and only routes import it.
- Inside a feature, imports of its own files are relative.
- A feature never imports another feature. What two features share moves to `src/domains/<name>/`.
- A feature documents itself in a `README.md` at its root, which every feature has; the [index of features](../04-features/README.md) is the entry table.

Put in a feature: components tied to a business area, mutation hooks, UI stores, Zod schemas, business types, and thin API modules (`*.api.ts`), for instance for an endpoint the OpenAPI contract does not describe.

Do not put in a feature: a widget with no business tie (`functionals/`), a generic UI component (`components/`), business logic that several features share (`domains/`).

`features/feature-flags/` contains three submodules, `rollout/`, `targeting/` and `variants/`. They carry API-backed business contracts with a single consumer, so they stay in the feature, and the check keeps them private to it. The anatomy of a feature is in the [overview](./overview.md#a-feature).

## `domains/`: business shared between features

[`src/domains/`](../../src/domains/) holds business modules that belong to no single feature but stay specific to one sub-domain: aggregated queries, read models, pure logic, forms and components. A domain owns no page and no route. Its `index.ts` is its public API.

A domain typically has `queries/` (query keys, options, invalidation helpers), `logic/` (statuses, statistics, relation builders), `types/` (read models) and, when needed, `components/`. For example:

- `domains/customer-management/` holds the read models that `customers`, `instances` and `connectors` share.
- `domains/release-management/` holds the release overview query, the release statuses and the shared component-catalog form, used by `releases`, `components`, `deployment-zones` and `instances`.
- `domains/crm-sync/` holds the per-entity CRM sync read model and its display components.
- `domains/billing/` holds what the billing screens share: the capabilities every billing screen gates on, the scope each action needs, money, period and status components, the invoice preview, and how a refusal of the API is shown.

Put in a domain:

- aggregated query options used by several features;
- read models and projection types;
- pure domain logic;
- forms and flows shared by features of the same sub-domain;
- business components shared by several features;
- modules that talk to an external service (an SDK, a network client) and carry its business vocabulary, even when they expose widgets.

Do not put in a domain: pages, route ownership or purely technical layouts/helpers (`lib/`, `hooks/`, `components/`, `functionals/`). A shared business shell consumed directly by sibling features may live in a domain: the release-management shell groups its business URLs, labels and entity icons there, while each feature still owns its page.

A shared module that looks like UI orchestration but carries business slugs or a network client belongs in `domains/`, not in `functionals/`. Splitting it is not an option: `functionals/` cannot import `domains/`, so the whole module moves. `domains/crm-sync/` is the reference case.

## `functionals/`: generic widgets

[`src/functionals/`](../../src/functionals/) holds complex, generic UI that several independent consumers share: `page`, `table`, `filters`, `detail-card`, `step-stack` and the like. A functional can also provide a shared navigation shell. It carries no business contract, no read model and no API client. See [functionals.md](./functionals.md).

- Unlike `components/`, a functional has non-trivial internal UI logic and at least two independent consumers; `components/` holds simple presentational pieces.
- Unlike `features/`, which own screens and route-facing mutations, a functional orchestrates shared UI.
- Unlike `domains/`, which carry business contracts, read models, aggregated queries and pure logic, a functional carries UI orchestration.

Where things go:

| Example | Where |
| --- | --- |
| Destructive button with confirmation | `components/destructive-action-button.tsx` |
| Shared page layout | `functionals/page/` |
| Data table, table card, actions column, delete and linked-items dialogs | `functionals/table/` |
| Route tabs, active tab by path prefix | `functionals/route-tabs/` |
| Shared business shell of `/releases/**` | `domains/release-management/components/` |
| Large form dialog with a discard confirmation | `functionals/stacked-form-dialog/` |
| CEL editor with Monaco completion | `functionals/cel-editor/` |
| Targeting rules list and editor | `features/feature-flags/targeting/` |
| Variants list and editor | `features/feature-flags/variants/` |
| Aggregated query over releases, deployment zones and instances | `domains/release-management/queries/` |
| A license's entitlements table | `features/licenses/components/` |
| A hook tied to one screen, such as the dashboard metrics | `features/dashboard/hooks/` |

## `hooks/`: shared hooks

[`src/hooks/`](../../src/hooks/) holds React hooks with no business logic that several features share. `form.ts` is the most important one: it exports `useAppForm`, `withForm`, `withFieldGroup` and `createFormSubmitHandler`, and wires the lazy-loaded field components of `components/form/` into TanStack Form. Hooks import only `components/`, `hooks/` and `lib/`.

A hook used by one feature stays in `features/<name>/hooks/` and moves here when a second feature needs it: see "Extract late" in [Principles](../AI_CONTEXT.md#principles).

## `lib/`: infrastructure

[`src/lib/`](../../src/lib/) holds the low-level modules that configure third-party tools and the small utilities the whole app uses. It is the lowest layer: it imports only itself and `api-client/`.

| Path | What it holds |
| --- | --- |
| `api/` | Wiring of the generated REST client: base URL, auth interceptor, `ApiError` wrapping; pagination helpers; query options that fetch every page of a list (`all-pages-query-options.ts`, built on the generated client); the generated `scopes.gen.ts` and `operation-scopes.gen.ts` |
| `auth-token.ts`, `local-auth.ts`, `granted-scopes.ts` | Resolution of the bearer token, the local dev-token mode, and the scopes the token carries (decoded for display only, never verified) |
| `graphql-client.ts` | The small `fetch` client for GraphQL |
| `errors/` | `ApiError`, `handleApiError`, `getApiErrorMessage`, error codes |
| `i18n/` | i18next configuration and the `en` and `fr` locales |
| `settings/` | Settings persisted in `localStorage` through TanStack DB |
| `detail/`, `navigation/` | Helpers for detail pages and breadcrumbs |
| `feature-flags.ts` | Evaluation of the flags the app gates its own features on, through OpenFeature and its OFREP web provider |
| `external-id.ts` | Browser-side derivation of an organization id, which has to match the server's (`api/pkg/externalid`) |
| `optimistic-mutations.ts`, `monaco-workers.ts` | Callbacks for optimistic deletes and invalidation on success; Monaco worker configuration |
| `logger.ts`, `utils.ts`, `debounce.ts`, `app-locale.ts`, `format-date.ts`, `money.ts`, `decimal.ts`, `download-blob.ts`, ... | Cross-cutting utilities; `cn` is in `utils.ts`; `app-locale.ts` names the language that numbers, money and dates are written in; `money.ts` formats and converts amounts without a float (BigInt and decimal strings), with the minor-unit exponents of the API in `currency-exponents.ts`; `decimal.ts` writes and adds the decimal strings the API carries quantities in, digit for digit; `download-blob.ts` saves a file the page holds or an export the API streams; `file-stamp.ts` writes the UTC moment of a download into the name of its file |

`lib/` is infrastructure plus a few bridges to the product. `data-model-icons.ts` maps each entity to an icon and `navigation/segment-labels.ts` maps URL segments to labels, because the whole app shares that vocabulary. `feature-flags.ts` names a product flag (`DEMO_SANDBOX_FLAG`) and `external-id.ts` repeats a server-side derivation. Feature screens and mutations stay out of `lib/`.

## `routes/`: TanStack routes

[`src/routes/`](../../src/routes/) uses file-based routing. Routes are thin assemblers: each connects a URL to a feature component.

```txt
routes/
├── __root.tsx                 # global layout
├── index.tsx                  # redirect to /dashboard
├── feature-flags/
│   ├── index.tsx              # list
│   ├── new/index.tsx          # create
│   └── $featureFlagSlug/      # detail: a layout route and its tab routes
│       ├── route.tsx
│       ├── index.tsx
│       └── targeting.tsx
├── customers/
│   ├── route.tsx              # layout route: Suspense around the Outlet
│   ├── index.tsx
│   └── $customerSlug/
└── -components/               # app shell: side navigation, breadcrumbs
```

- Dynamic segments are usually named after the slug they carry: `$customerSlug`, `$featureFlagSlug`, `$zoneSlug`. `integrations/connectors/$connectorId.tsx` carries a connector id.
- A `route.tsx` is a layout route. Detail pages use one, with tab routes beside it.
- The router ignores names that start with `-`. `routes/-components/` is the app shell, not a route.

In a route: the `loader`, `beforeLoad` (for example the page title of the breadcrumb), `validateSearch`, `Route.useParams()`, `useSuspenseQuery` on the main query, and the render of the feature's root component.

Never in a route: mutations, business logic, data filtering, detailed presentational JSX. Lint refuses the `useMutation`, `useState` and `useReducer` imports in route files; under `routes/-components/` only `useMutation` is refused. See [routes-as-assemblers.md](../03-patterns/routes-as-assemblers.md).
