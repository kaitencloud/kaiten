# Architecture overview

The console is a single-page React application in `app/`. It talks to the Go API in `api/` over REST and GraphQL, through clients generated from the API contract. This page covers the stack, the shape of the code and how data moves. The rules are in [AI_CONTEXT.md](../AI_CONTEXT.md); the folder guide is [folder-structure.md](./folder-structure.md).

## Stack

Exact versions are in `app/package.json` and in the `catalog` of `pnpm-workspace.yaml`.

| Area | Technology |
| --- | --- |
| Language | TypeScript 7, the native compiler. `packages/api-codegen` uses TypeScript 6 instead (catalog `codegen`), because `@hey-api/openapi-ts` needs the JavaScript compiler API that TypeScript 7 does not expose. |
| UI | React 19, Tailwind CSS 4. Design tokens come from `@kaitencloud/theme` (`packages/theme`); `src/tokens.css` adds the app's own. |
| Primitives | shadcn/ui's Base UI components (`@base-ui/react`), installed with the `base-vega` style. Headless primitives are imported only under `src/components/ui/`. |
| Routing | TanStack Router 1: file-based routes, automatic code splitting. |
| Server state | TanStack Query 5. |
| Tables | TanStack Table 9. |
| Feature UI state | TanStack Store. TanStack DB holds the settings persisted in `localStorage`. |
| Forms | TanStack Form 1 with Zod 4. |
| REST | A client generated from `app/openapi.yaml` by `@hey-api/openapi-ts`: the hey-api `fetch` client, with the `zod` and `@tanstack/react-query` plugins. |
| GraphQL | Types and documents generated by `graphql-codegen` (`client` preset); a small `fetch` client in `src/lib/graphql-client.ts`. |
| Auth | Clerk (`@clerk/react`). With `VITE_LOCAL_AUTH=true`, a local account switcher with dev tokens replaces it, for local stacks. |
| i18n | i18next and react-i18next, in English and French. |
| Editors | Monaco (`functionals/code-editor`, `functionals/cel-editor`) and CodeMirror (the JSON form field). The CEL editor gets its local syntax check from a Rust engine compiled to WebAssembly (`app/cel-engine`, built by `pnpm run build:wasm`); `cel-js` parses expressions for the formatter, and the server lint gives the verdict for targeting rules. |
| Toolchain | Vite+ (the `vp` CLI: Vite, Vitest, Oxlint, Oxfmt) and pnpm. |
| Tests | Vitest, Storybook, Playwright, Mock Service Worker. |

## How the code is organised

`app/src` is split into layers by folder. From the bottom: `lib/` (infrastructure), `hooks/`, `components/` (generic UI), `functionals/` (generic widgets), `domains/` (business modules shared between features), `features/` (one folder per product area) and `routes/` (URLs, which assemble features). The generated `api-client/` sits beside them. Imports go down that list, except that `hooks/` and `components/` may import each other, and features never import each other or `routes/`.

The layer table, the placement rules and the enforced import rules are in [AI_CONTEXT.md](../AI_CONTEXT.md#layers). The dependency matrix and the folders are in [folder-structure.md](./folder-structure.md).

### A feature

A feature is a self-contained module under `src/features/<name>/`. It owns its screens, its mutation hooks, its UI state and its form schemas, and its `index.ts` is the route-level API: routes import from `@/features/<name>`, and nothing else does.

```txt
features/<name>/
├── components/   # screens and pieces, with stories/ and __tests__/ beside them
├── hooks/        # mutation and view-model hooks
├── queries/      # query options built on the generated client
├── schemas/      # Zod schemas for the feature's forms
├── store/        # TanStack Store, for complex UI state
├── types/
├── utils/
├── index.ts      # the public API, for routes
└── README.md
```

A feature has the folders it needs; `components/`, `index.ts` and `README.md` are in every feature, and the README documents the feature. See the [feature template](../04-features/_template/FEATURE_TEMPLATE.md) and the [index of features](../04-features/README.md).

```ts
// app/src/features/customers/index.ts
export {
  CustomerDetailPageContent,
  CustomerFormDialog,
  CustomersPageContent,
} from './components';
export { customerQueryOptions } from './queries';
```

### Domains and functionals

`src/domains/<name>/` holds the business code that several features share: aggregated queries and their query keys, read models, pure logic, and forms or components used by more than one feature. A domain never owns a page. For example, `domains/customer-management/` serves `customers`, `instances` and `connectors`; `domains/release-management/` serves `releases`, `components`, `deployment-zones` and `instances`. Its `index.ts` is its public API, and routes may load its query options.

`src/functionals/<name>/` holds generic widgets and layouts with real logic and several independent consumers (`page`, `table`, `filters`, `detail-card`, `step-stack`, ...). A functional carries no business contract and no API client. See [functionals.md](./functionals.md).

## Routing

Routes use TanStack Router with file-based routing and automatic code splitting. They are thin: a route declares its URL, loads data and renders a feature component.

```txt
routes/
├── __root.tsx          # app layout: header, side navigation, breadcrumbs, Outlet
├── index.tsx           # redirects to /dashboard
├── customers/
│   ├── route.tsx       # layout route: Suspense around the Outlet
│   ├── index.tsx       # the list
│   ├── new/            # create
│   └── $customerSlug/  # detail: a dynamic segment
├── ...
└── -components/        # app shell, not a route: the router ignores the "-" prefix
```

A route loads its data with `ensureQueryData`, and the feature component reads the same query with `useSuspenseQuery`:

```tsx
// app/src/routes/customers/index.tsx
import { createFileRoute } from '@tanstack/react-router';
import { customersWithInstancesQueryOptions } from '@/domains/customer-management';
import { CustomersPageContent } from '@/features/customers';

export const Route = createFileRoute('/customers/')({
  component: CustomersPageContent,
  loader: ({ context }) =>
    context.queryClient.ensureQueryData(customersWithInstancesQueryOptions),
});
```

```tsx
// app/src/features/customers/components/customers-page-content.tsx (abridged)
export function CustomersPageContent({ children }: { children?: ReactNode }) {
  const { data: customers } = useSuspenseQuery(
    customersWithInstancesQueryOptions,
  );
  // ...render the page from `customers`
}
```

A small create or edit form opens in a dialog controlled by the URL: a layout route (`route.tsx`) keeps the parent page mounted and renders the dialog through its `Outlet`. See [dialog-via-route.md](../03-patterns/dialog-via-route.md) and [routes-as-assemblers.md](../03-patterns/routes-as-assemblers.md).

## Data

The `openapi.yaml` that the Go API generates is the source of truth for the REST types, Zod schemas and calls, apart from the few endpoints it does not describe (see [Generated code](../AI_CONTEXT.md#generated-code)). [api-contract.md](./api-contract.md) says where each contract lives and [api-generation.md](./api-generation.md) says what `pnpm run generate` produces. [data-flow.md](./data-flow.md) follows a read and a write end to end.

### REST

`@hey-api/openapi-ts` writes the REST client into `src/api-client/`:

```txt
api-client/
├── client.gen.ts                 # creates the client (base URL /api by default)
├── client/, core/                # the hey-api fetch client runtime
├── sdk.gen.ts                    # one typed function per operation
├── types.gen.ts                  # TypeScript types
├── zod.gen.ts                    # Zod schemas
├── @tanstack/react-query.gen.ts  # query options, mutations and query keys
└── graphql/                      # GraphQL types and the graphql() document function
```

The generated client is only created; `src/lib/api/configure-api-client.ts` configures it. `main.tsx` imports `lib/api/bootstrap.ts` once before the route tree, setting the base URL from `env.API_URL`, a request interceptor that sends the current bearer token, and an error interceptor that wraps failures in `ApiError`. The token comes from `getAuthToken()` in `src/lib/auth-token.ts`: the stored dev token when `VITE_LOCAL_AUTH=true`, otherwise the Clerk session token, with the `__session` cookie as a fallback.

### GraphQL

GraphQL serves the read models that join several entities: the dashboard, customers with their instances, the release overview, the audit trail. Writes go through REST: the GraphQL schema has queries only. Documents are written with `graphql()` in `*.queries.ts` files. `graphql-codegen` reads the `.graphqls` schemas under `api/` and those documents, and `graphqlClient` in `src/lib/graphql-client.ts` sends them with the same bearer token.

### Regenerating

```bash
# from the repository root: the OpenAPI specs, from the Go source
task generate:oas

# from app/: the REST and GraphQL clients
pnpm run generate
```

`src/api-client/` is git-ignored, so run `pnpm run generate` after a fresh clone.

## State

| Kind | Tool | Holds | Example |
| --- | --- | --- | --- |
| Server state | TanStack Query | API data, cache, invalidation | `useSuspenseQuery(customersWithInstancesQueryOptions)` |
| Feature UI state | TanStack Store | UI state of one feature | `useLicenseVersionFormStore()` |

Details and the decision tree are in [state-management.md](../03-patterns/state-management.md). After a mutation, invalidate with the generated query key functions: see [query-key-invalidation.md](../02-conventions/query-key-invalidation.md).

## Forms

Forms use TanStack Form with Zod validation and lazy-loaded field components, through `useAppForm` from `src/hooks/form.ts`. The rendered `<form>` uses `createFormSubmitHandler` from the same module, so `preventDefault()` and `stopPropagation()` always run.

```tsx
// app/src/features/customers/components/customer-form.tsx (abridged)
import { createFormSubmitHandler, useAppForm } from '@/hooks/form';

const form = useAppForm({
  defaultValues: customer
    ? customerToFormValues(customer)
    : initialCustomerFormValues,
  validators: { onChange: customerFormSchema },
  onSubmit: async ({ value }) => {
    // call the create or update mutation, then navigate or show a toast
  },
});

return (
  <form onSubmit={createFormSubmitHandler(form.handleSubmit)}>
    {/* fields */}
  </form>
);
```

A form schema starts from the generated one in `api-client/zod.gen.ts` when the form matches an API payload: `customerFormSchema` is built from `zCustomer`. It lives beside the form or in the feature's `schemas/` folder, or in a domain when several features share the form. See [forms.md](../03-patterns/forms.md).

## Tests

| Level | Tool | Command, from `app/` | Where |
| --- | --- | --- | --- |
| Unit | Vitest, in jsdom | `pnpm run test` | `src/**/*.test.ts(x)` and `scripts/**/*.test.ts` |
| Component | Storybook stories, run as tests by the Vitest addon in Chromium | `pnpm run test:stories` | `*.stories.tsx` next to the code, usually in a `stories/` folder |
| E2E, Storybook | Playwright against Storybook, with visual regression. Skipped locally unless `VISUAL_TESTS=true` | `VISUAL_TESTS=true pnpm run test:e2e` | `e2e/tests/` |
| E2E, application | Playwright against the dev server, with auth bypassed and the API mocked by Mock Service Worker | `pnpm run test:e2e:app` | `e2e/app/` |

Unit tests cover stores, schemas, domain logic and utilities. Stories are visual documentation and render smoke tests; the ones coupled to the router, query client, forms or API stay out of the Storybook test run (`storybookTestExclude` in `app/vite.config.ts`) and the application E2E suite covers them. `pnpm run test:coverage` reports coverage without a global threshold, and leaves out `components/ui/`, `routes/`, generated code and stories (see `app/vite.config.ts`). The scripts are listed in [scripts.md](../00-getting-started/scripts.md).
