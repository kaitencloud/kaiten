# Internationalization

Text a user can read goes through i18next; a component does not hard-code it. English (`en`) is the reference locale. French (`fr`) is enabled: the language is selectable in the settings, in the application section.

## Setup

The stack is [i18next](https://www.i18next.com/) with `react-i18next`. Components read translations with `useTranslation()`.

```
app/src/lib/i18n/
├── config.ts        # i18next initialisation and changeLanguage()
└── locales/
    ├── en.ts        # reference locale
    └── fr.ts        # French: the same key tree as en.ts
```

`src/main.tsx` imports `@/lib/i18n/config` for its side effect. The module does four things:

- It registers `en` and `fr` as the `translation` resources. There is one i18next namespace only; the prefixes described below are ordinary top-level keys of the locale objects.
- It reads the initial language from the app settings (`@/lib/settings`) and falls back to `en` when none is stored. `en` is also the fallback for a key missing from the active language.
- It sets `compatibilityJSON: 'v4'` (plural suffixes `_one` and `_other`) and `escapeValue: false`, because React already escapes text.
- It exports `changeLanguage(code)`, which changes the active language and stores it in the app settings, so the choice survives a reload. The language selector in `features/settings/components/application-settings-section.tsx` calls it.

`useTranslation()` takes no argument in this codebase: there is no `keyPrefix` and no second namespace, and keys are always written in full. `t` does not check keys against `en.ts`, so a typo does not fail the type check: the screen shows the key itself, or the inline default if the call has one. `pnpm run check:i18n-keys` catches the typo instead (see [Checks](#checks)).

## Key structure

A key is the path of a string in the `en.ts` object, for example `Pages.Licenses.Mutation.Form.Labels.name`. The first level names the kind of text:

| Prefix | Holds |
| --- | --- |
| `Common.*` | Shared labels and messages: `Common.cancel`, `Common.save`, `Common.confirmDeleteTitle`. |
| `Pages.<Name>.*` | The screens of one area of the console, named after it: `Pages.Customers`, `Pages.Licenses`, `Pages.FeatureFlags`, `Pages.Settings`. |
| `Features.<Name>.*` | Text of a module that is not one screen: a domain (`Features.AuditTrail`, used by `domains/audit-trail`), a submodule of a feature (`Features.Targeting` and `Features.Variants`, used by `features/feature-flags`), or text shared by several features (`Features.Releases`, used by `features/deployment-zones`, `features/releases` and `domains/release-management`). |
| `Functionals.*` | Text owned by a functional, such as `Functionals.CelEditor.*`. |
| `Errors.*` | Route error, not-found and restricted-access pages, and `Errors.api.<CODE>`, the generic message of each API error code. |
| `Sign.*` | Wording for sign-in and sign-up. No code reads these keys today; do not add text here. |

The areas with a create and edit form (`Customers`, `Licenses`, `Entitlements`) group that text under `Mutation.Form`, in `Labels`, `Placeholders`, `Descriptions` and `Errors`. This is an abridged excerpt of `Pages.Licenses`:

```typescript
// app/src/lib/i18n/locales/en.ts (abridged)
Pages: {
  Licenses: {
    title: 'Licenses',
    subtitle: 'Manage licenses and entitlement limits',
    Table: {
      Columns: { name: 'Name', version: 'Version' },
    },
    Mutation: {
      titleNew: 'New License',
      titleUpdate: 'Edit License',
      Form: {
        Labels: { name: 'Name' },
        Placeholders: { name: 'Bronze' },
        Descriptions: { slug: 'Auto-generated — edit to set a custom one.' },
        Errors: { name: 'Name is required' },
        createSuccess: 'License created successfully',
        createButton: 'Create License',
        updateButton: 'Update License',
      },
    },
  },
},
```

Look at a neighbouring area (`Pages.Customers`, `Pages.Entitlements`) before adding a new one, and reuse its groups. Not every area has a `Mutation` group: `Pages.Releases` keeps its form text under `Form`.

### Naming

| Level | Case | Examples |
| --- | --- | --- |
| Prefix, area and structural group | PascalCase | `Pages`, `Licenses`, `Mutation`, `Form`, `Labels`, `Placeholders`, `Descriptions`, `Errors`, `Table`, `Columns`, `Detail` |
| Group named after a piece of content (a card, a section) | camelCase | `Pages.Customers.Detail.customerDetails.fields.name` |
| Last segment | camelCase | `title`, `createButton`, `warningDelete` |
| Form field under `Labels`, `Placeholders`, `Descriptions`, `Errors` | camelCase, the name of the field | `Labels.versionName` |
| Value of an API enum | the API value | `Pages.Entitlements.EntitlementTypes.BOOLEAN` |

## Using translations

### In a component

```tsx
import { useTranslation } from 'react-i18next';

const { t } = useTranslation();

<Button>{t('Common.cancel')}</Button>
```

### Interpolation

`{{name}}` in the text, the values in the second argument:

```typescript
// en.ts: confirmDeleteDescription: 'This action cannot be undone. This will delete {{name}}'

// app/src/features/customers/components/customer-detail/customer-detail-header.tsx
t('Common.confirmDeleteDescription', { name: customer.name })
```

### Plurals

Give the key both suffixes in both locales, and pass `count`:

```typescript
// en.ts, inside Functionals.CelEditor
issueCount_one: '{{count}} issue',
issueCount_other: '{{count}} issues',

// app/src/functionals/cel-editor/components/cel-editor-status.tsx
t('Functionals.CelEditor.issueCount', { count: issues.length })
```

### Keys built at run time

A value of an API enum selects its translation. Every value the API can return needs a key in both locales, because `check:i18n-keys` cannot read a key assembled from a template:

```tsx
// app/src/features/entitlements/components/entitlement-type-display.tsx
{t(`Pages.Entitlements.EntitlementTypes.${entitlementType}`)}
```

### Context

A text that reads differently for a few values of one property has one key per value, suffixed with the value, and a plain key for the rest. The call passes the value as `context`, and i18next picks `<key>_<context>` when it exists and `<key>` otherwise:

```tsx
// en.ts: release: 'Releasing issues the invoice.', release_STRIPE: 'Releasing issues the invoice, and Stripe collects it.'

// app/src/features/billing/components/invoice-detail/hold-banner.tsx
t('Pages.Billing.Invoices.Detail.Hold.release', { context: invoice.providerKind })
```

A `context` of `undefined` is no context, so a call can pass one only where it applies (`context: endedAs` in `invoice-handoff-block.tsx`). Write the suffixed keys in both locales: `check:i18n-keys` reads a call that passes `context` as asking for the key and its suffixed forms, and `check:i18n-parity` compares them like any other key. Use this for a value of an API enum that changes a sentence, not for the label of the value itself (see [Keys built at run time](#keys-built-at-run-time)).

### Outside a component

A route `beforeLoad` or a plain function has no hook. Import the shared instance and call `i18n.t`, or receive `t` as a parameter typed `TFunction` from `i18next`, as the helpers of `domains/audit-trail` do:

```typescript
// app/src/routes/customers/instances/$instanceSlug/audit-trail.tsx
import i18n from '@/lib/i18n/config';

getTitle: () => i18n.t('Pages.Customers.Instances.Detail.tabs.auditTrail'),
```

### In forms

Form field components and `SubmitButton` take already translated strings. The button takes them through its `label` prop, not as children:

```tsx
// app/src/features/customers/components/customer-form-fields.tsx (abridged)
<field.TextField
  label={t('Pages.Customers.Mutation.Form.Labels.name')}
  placeholder={t('Pages.Customers.Mutation.Form.Placeholders.name')}
  description={t('Pages.Customers.Mutation.Form.Descriptions.name')}
/>

// app/src/features/customers/components/customer-form.tsx (abridged)
<form.SubmitButton
  label={
    customer
      ? t('Pages.Customers.Mutation.Form.updateButton')
      : t('Pages.Customers.Mutation.Form.createButton')
  }
/>
```

A validation message in a Zod schema is a key, not a sentence. The field runs its first error message through `t`, so `'Pages.Licenses.Mutation.Form.Errors.name'` is displayed in the active language. A message that is not a key is displayed as written, in English. See [forms](../03-patterns/forms.md#validation-schemas).

### API errors

For an API error, `getApiErrorMessage` from `@/lib/errors` returns the message the server sent, when there is one, and otherwise the translation of `Errors.api.<CODE>` in the active language. The result is ready to display; do not pass it through `t` again. See [error handling](./error-handling.md).

## Adding a key

1. Add the key to `app/src/lib/i18n/locales/en.ts`, under the prefix and group it belongs to.
2. Add the same path to `fr.ts`, with the French text.
3. Use it with `t('<full key>')`.
4. From `app/`, run `pnpm run check:i18n-parity` and `pnpm run check:i18n-keys`.

For a new API error code, add it to `API_ERROR_CODES` in `app/src/lib/errors/types.ts`, then add `Errors.api.<CODE>` to both locales.

### Inline defaults

`t` accepts an English default as its second argument, and a share of the existing calls uses it:

```tsx
// app/src/components/combobox.tsx
t('Common.none', 'None')
```

The key exists in both locales, so the default is never displayed. `pnpm run check:i18n-keys` fails on a key that `en.ts` does not have, with or without a default, so a default cannot hide a missing key. New code declares the key in both files and calls `t('<key>')` without a default.

## Checks

Run from `app/`. All three run in the CI (`.github/workflows/app-ci.yml`) and in `pnpm run check:ci`.

| Command | Fails when |
| --- | --- |
| `pnpm run check:i18n-parity` | A key path exists in `en` and not in `fr`, or the reverse (`app/scripts/check-i18n-parity.ts`). |
| `pnpm run check:i18n-keys` | The code asks for a key that `en.ts` does not have (`app/scripts/check-i18n-keys.ts`). It reads the first argument of `t()` calls, the `i18nKey` prop of `<Trans>` and the full-key string literals that tables store, including keys known only through an inline default. Tests, stories and generated code are not scanned. |
| `pnpm run check:api-error-i18n` | An entry of `API_ERROR_CODES` has no `Errors.api.<CODE>` in `en`, or an `Errors.api` key is not a code (`app/scripts/check-api-error-i18n.ts`). A pre-push hook runs it when `src/lib/errors/types.ts` or a locale file changes. |

The parity check compares the two locale files with each other and does not read the `t()` calls. `check:i18n-keys` compares the keys the code asks for with `en.ts`. A key built at run time (`t(key)`, a template string) is counted but not checked, and no command detects a hard-coded string: review covers both.

## Tests and stories

- Unit tests run against a minimal i18next instance (`app/src/__tests__/test-i18n.ts`, loaded by the setup file). It holds almost no translation and returns a missing key as the key itself, so a test that does not mock `react-i18next` sees key paths, not English text.
- To test what a component prints in a language, add the bundle to that instance and switch to it: `testI18n.addResourceBundle('fr', 'translation', fr, true, true)` in `beforeAll`, `await testI18n.changeLanguage('fr')` in the test, and `changeLanguage('en')` in `afterEach`. Assert the translated word and, for a label that used to print a raw English word, that the English word is gone (`features/components/components/__tests__/component-releases-display.test.tsx` does). An English-only test cannot catch a label that skips `t()`, since the raw word and its translation are the same string.
- An E2E spec switches language with `persistLanguage(page, 'fr')` from `app/e2e/app/_support/language.ts`, then reloads the page and goes on to assert (`e2e/app/i18n/i18n.locale.spec.ts` and `e2e/app/release-management/release-status.read.spec.ts`). A spec that navigates afterwards uses `startInLanguage(page, 'fr')` from the same file instead, before its first `goto`: the first load of a page under Mock Service Worker reloads once on its own, and a `page.reload()` of the spec races that reload, so a later `goto` is sometimes interrupted by it (`e2e/app/billing/billing.french.spec.ts`).
- Storybook wraps every story in an `I18nextProvider` with the app instance (`app/.storybook/preview.tsx`), so stories show the real English text.
